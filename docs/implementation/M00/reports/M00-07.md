## Decisões locais

- **A suite type is declared once**, in `lib/gates/suite_types.rb`, and read by both
  `bin/test --type` and the RSpec configuration. Two lists would drift, and the CI
  pipeline schedules by type.
- **The barrier is proven by reproducing a race before preventing one.** A
  concurrency helper nobody showed can expose a lost update gives false
  confidence: every test using it would pass whether or not the code was correct.
  The first example forces both writers to read before either writes and asserts
  the counter reads `1`; the second adds `SELECT ... FOR UPDATE` and asserts `2`.
- **A barrier raises on timeout rather than hanging.** A broken concurrency test
  should fail in ten seconds with `1/2 arrived`, not stall the suite.
- **`:concurrent` examples run outside the example transaction.** Threads cannot
  see each other's uncommitted rows, so the transaction would make the race
  impossible to reproduce. They clean up after themselves.
- **Each parallel worker gets its own database**, suffixed by `TEST_ENV_NUMBER`,
  which `unique_namespace` also reads. Without the suffix a "parallel" run is
  several workers overwriting each other — it fails intermittently and blames the
  code.
- **The quarantine expires.** After its deadline the example runs again, so a
  quarantine cannot decay into a permanent skip. A `security` example is refused
  one outright: an intermittent failure there blocks release until understood.
- **Evidence is written on every run**, not only in CI. "The suite passed" is not
  release evidence; which commit, which branch, which environment, which database,
  how long and how many examples is.

## Acceptance Criteria

- [x] 1. `bin/test` runs the backend suite against **real PostgreSQL** and exits
      `0` — `spec/integration/test_harness_spec.rb` asserts the adapter is
      PostgreSQL, not SQLite.
- [x] 2. Suites are separable by type and individually runnable — the six types are
      declared once in `lib/gates/suite_types.rb`, `bin/test --type <name>` runs
      each, and `spec/integration/test_harness_spec.rb` asserts the declared types
      match the directories on disk.
- [x] 3. Execution order is random by default and the seed is reported — asserted
      against `RSpec::Core::Ordering::Random`; `bin/test --seed` replays it.
- [x] 4. A concurrency helper with multiple connections and an explicit barrier
      exists, **proven by reproducing a lost update without the lock and
      preventing it with one** — `spec/support/concurrency.rb` and the two
      examples in `spec/integration/test_harness_spec.rb`.
- [x] 5. The clock is controllable, with a test that exercises an expiry without
      waiting — a 30-minute lease is expired by `travel(31.minutes)`, and the
      clock is asserted to be restored afterwards.
- [x] 6. Parallel execution uses unique namespaces and cleanup is idempotent after
      a simulated crash — each worker has its own database; `unique_namespace`
      carries the worker number and the pid; cleanup run three times returns
      `1, 0, 0`.
- [x] 7. Factory lint passes and no factory creates more than needed —
      `FactoryBot.lint` is asserted, and creating one checkpoint leaves exactly one
      row.
- [x] 8. The report includes commit, environment, duration and result per suite —
      `tmp/test-results/rspec-metadata.json`, asserted by a spec.
- [x] 9. No fixture contains real data or PII — `spec/factories/infrastructure_checkpoints.rb`
      generates every name from a sequence, and `spec/integration/test_harness_spec.rb`
      asserts the built name matches `checkpoint-<n>`. There are no fixture files.

## Pendências / conflitos

- **No specification conflict found.** SC-03 is applied as written.
- Random order exposed a real defect while this Story was being written: two spec
  files both defined a top-level `ROOT` constant, so whichever loaded second won
  and the first file's expectations ran against the wrong value. Renamed to
  `REPOSITORY_ROOT` and `LINT_PROBE_ROOT`. This is exactly the class of failure
  random ordering exists to surface.
- `bin/test --parallel` requires `bundle exec rake parallel:prepare` once, to
  create the worker databases. `bin/setup` (M00-06) runs it.
- Coverage measurement is not part of this Story and Annex I §22.1 warns against
  treating it as a target. If it is added later it is as a trend, not a gate.
