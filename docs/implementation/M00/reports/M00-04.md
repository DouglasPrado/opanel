## Decisões locais

- **Pages are resolved eagerly and a missing one throws by name**, listing what is
  available. The resolver lives in `lib/resolve-page.ts` rather than inline in the
  entry point so it can be unit-tested in M00-08.
- **`ErrorsController` is wired through `config.exceptions_app`**, not a
  `rescue_from` in `ApplicationController`. It covers exceptions raised anywhere in
  the stack, including routing errors, and it does not put a broad rescue in the
  controller hierarchy.
- **Error messages are fixed per status.** The exception's own message can carry a
  query, a filesystem path or a credential, and this response is rendered for a
  user. What actually happened stays in the server log, correlated by request id.
- **CSRF failures raise** (`with: :exception`) rather than resetting the session.
  A rejected request should be visible, not silently anonymous.
- **Dark mode follows the system unless `data-theme` is set.** E2E runs and
  screenshots need a deterministic theme, so the override is not cosmetic.
- **CSP relaxations are scoped to development.** `unsafe-eval`, `unsafe-inline`
  and the Vite origin exist only while the dev server is the origin of the
  modules; a built asset needs none of them, and a spec asserts `unsafe-eval` is
  absent outside development.
- **HSTS is left to `config.force_ssl`** in production. Emitting it from a
  non-TLS environment locks a developer out of their own machine.
- **The example page uses plain elements, not new primitives.** M00-05 imports the
  component library, and the Reuse Gate applies from that point; building a Button
  here would be building exactly what is about to arrive.

      `spec/security/inertia_shared_props_spec.rb`, including a planted `apiToken`

- [x] 9. No Next.js file and no REST route created only for the UI — asserted in
      `spec/architecture/repository_layout_spec.rb` (M00-01) and in
      `spec/requests/inertia_spec.rb` (no `/api/` route).

## Dependências novas

All of the following are the approved stack (`docs/AGENT_RULES.md`, "Approved
stack": React + TypeScript over Inertia.js, bundled with Vite, styled with
Tailwind). They are recorded for the ledger rather than argued as new choices.

### Dependency: `inertia_rails` `3.22.0`

- **Story:** `M00-04`
- **Ecosystem:** rubygems
- **Problema resolvido:** the Rails side of the Inertia protocol — page responses,
  shared props, asset versioning, redirect semantics.
- **Alternativas avaliadas:** hand-rolling the protocol.
- **Por que não bastam:** the protocol has version negotiation, partial reloads and
  redirect rules; reimplementing it is strictly more code and more risk.
- **Maintenance:** actively maintained, tracks the Inertia protocol releases.
- **Security:** no known advisory. It serializes props into HTML, which is exactly
  why `spec/security/inertia_shared_props_spec.rb` exists.
- **License:** MIT — compatible.
- **Escopo:** proportional.
- **Impacto de longo prazo:** alto, and already accepted by the architecture.
- **Lockfile:** `Gemfile.lock` — `3.22.0`.

### Dependency: `vite_rails` `3.11.1`

- **Story:** `M00-04`
- **Ecosystem:** rubygems
- **Problema resolvido:** Vite integration — dev server proxying, manifest lookup,
  digested asset tags, build orchestration.
- **Alternativas avaliadas:** Propshaft with an import map; jsbundling-rails.
- **Por que não bastam:** the approved stack names Vite; an import map gives no
  TSX transform and no HMR.
- **Maintenance:** actively maintained.
- **Security:** no known advisory; the dev server is development-only.
- **License:** MIT — compatible.
- **Escopo:** proportional.
- **Impacto de longo prazo:** alto, and already accepted.
- **Lockfile:** `Gemfile.lock` — `3.11.1`.

## Pendências / conflitos

- **No specification conflict found.** SC-01 is now enforced by code and by tests
  rather than by prose.
- `Procfile.dev` was generated by the Vite installer with only `web` and `vite`.
  M00-06 owns `bin/dev` and adds the Solid Queue worker to it.
- Component tests and the browser E2E harness are M00-08. This Story ships the
  request-level and security coverage only, as its Required Tests state.
- Running `bin/rails server -d` (daemonized) in development can die while Vite's
  `autoBuild` runs during the first request. The foreground server is unaffected,
  and `bin/dev` (M00-06) runs the Vite dev server alongside Rails, which is the
  supported path. Recorded so it is not rediscovered as a mystery.
