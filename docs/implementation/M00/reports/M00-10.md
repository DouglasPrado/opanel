## Decisões locais

- **A secret always blocks; a new Critical or High blocks; Medium and Low are
  reported.** Stated in the script rather than implied by exit codes, because a
  policy nobody can read is a policy nobody applies consistently.
- **An expired waiver blocks again automatically.** Without that the file becomes
  a list nobody has opened since, and the scanner it silences becomes decoration.
- **Expiry is evaluated in UTC** (`Time.now.utc.to_date`). `Date.today` would mean
  CI and a developer three timezones away disagree about whether a waiver is
  still valid, for three hours a day.
- **Waiving the secret scan requires recorded human approval.** An agent may not
  waive it: that is the one control standing between a leaked credential and a
  green build.
- **The allowlist lists fixture *values*, not spec files.** Allowlisting
  `spec/security/` wholesale would also hide a real secret that ended up there,
  which is precisely the case most worth catching.
- **Planted fixtures are deterministic, assembled from fragments.** An earlier
  version generated them randomly and was intermittently green, because gitleaks
  applies an entropy threshold a random string sometimes falls below. A flaky
  security test is a defect, not something to retry.

## Pendências / conflitos

**Corrected at fix attempt 03**, from that round's repair of the CI pipeline:
`spec/security/workspace_guardrail_spec.rb` opened with `require "english"`. macOS
resolves that to `English.rb` because its filesystem is case-insensitive, so the
file loaded here and on every developer machine, and failed to load on the Linux
runner — taking the whole `security-fast` job's `controls` command with it,
`0 examples, 1 error occurred outside of examples`. It is `require "English"`. It
is the only occurrence in the repository; `bin/setup:18` already had it right.

**Also corrected at fix attempt 03**, and the more serious of the two. With the
suite loading again, three of the planted-secret examples reported
`scanned ~0 bytes (0) — no leaks found` on the runner: the scan was not failing to
detect, it was not running. `config/security/gitleaks.toml` allowlisted
`tmp/.*`, unanchored, which matches **any** path containing `tmp/` — including
`/tmp`, where `Dir.mktmpdir` puts a scratch directory on Linux. The examples plant
their fixture in a scratch directory precisely to stay out of the repository's
allowlisted `tmp/`, and on Linux they planted it straight into the allowlist. The
entry is `^tmp/` now, which is what it always meant, and the fixture is planted
one level under a `tmp/` inside the scratch root so the path has the same shape on
every platform — an un-anchored entry fails the examples everywhere rather than
only where they happen to run. Verified both directions against `gitleaks 8.30.1`:

| Config | Fixture | Result |
|---|---|---|
| `tmp/.*` | `<scratch>/tmp/planted.txt` | `scanned ~0 bytes (0)`, no leaks — the defect |
| `^tmp/` | `<scratch>/tmp/planted.txt` | `scanned ~39 bytes`, `leaks found: 1` |
| `^tmp/` | repository scan, key planted in `tmp/probe-scan/` | no leaks — the repository's own `tmp/` is still allowlisted |

The other directory entries stay unanchored on purpose: `node_modules/` and
`vendor/bundle/` nest, and an allowlist that only covered the top-level copy would
be wrong. `tmp/` does not nest.
