## Decisões locais

- **The queue lives in the primary database**, not the separate `queue` database
  Rails 8 generates. It removes an operational moving part, and it does not make
  the broker authoritative: nothing in the design reads intent from a job row.
  Separating it later is a schema change, not a design change.
- **Solid Queue is the adapter in every environment**, including test and
  development. An in-process adapter lets a job pass locally and fail against a
  real queue — the exact defect a queue is supposed to surface.
- **No global retry policy.** A job that has not thought about its own failure
  modes does not retry. `retry_policy` refuses a non-positive `attempts`, so no
  policy is unbounded.
- **`InvalidPayload` is discarded, never retried.** Retrying malformed input just
  burns the queue.
- **Active Job's Module serializer removed.** Opanel has no job that legitimately
  passes a class, and the serializer constantizes a name read back from the
  database. Narrowing the payload vocabulary to inert types is cheap.
- **`bin/jobs` selects its supervisor mode by platform** — see Pendências.
- **Arguments are never logged.** A payload may reference a `SecretVersion`; the
  execution log is not where that gets discovered.

## Acceptance Criteria

- [x] 1. The worker runs as a process separate from the web server — `bin/jobs`
      is its own executable entry point; `spec/integration/queue_configuration_spec.rb`
      asserts it exists, is executable and starts the Solid Queue CLI, and the
      crash spec spawns it as a real OS process.
- [x] 2. An enqueued job executes and the result is observable in the log with
      `correlation_id` — `spec/integration/jobs_spec.rb` sets a correlation id at
      enqueue and finds it in the job's own log line, together with `job.performed`,
      the job class and the queue.
- [x] 3. The six logical queues exist as named configuration —
      `lib/opanel/queues.rb` and `config/queue.yml`, cross-checked by four
      examples: exact list, full coverage, no queue served twice, no `*` worker.
- [x] 4. A transient failure retries per the class policy and stops at the ceiling
      — `ExampleTransientFailureJob` declares 3 attempts; the counter reads exactly
      3 executions and a terminal failure is logged. The ceiling is asserted to be a
      positive integer, so "unlimited" cannot slip in.
- [x] 5. An invalid payload fails validation without applying any effect — three
      examples: a malformed name, an out-of-range argument, and proof that the
      discard happens once rather than being retried.
- [x] 6. A worker killed mid-execution does not duplicate the idempotent effect —
      `spec/integration/worker_crash_spec.rb` SIGKILLs the process group while
      `perform` is in progress, waits for the pruned process to fail its claimed
      execution, re-runs it, and asserts exactly one checkpoint row.
- [x] 7. `app/jobs/README.md` declares the handoff rule and the broker's
      non-durability — asserted in `spec/security/job_payload_spec.rb` so the
      document cannot quietly lose either rule.

## Dependências novas

### Dependency: `solid_queue` `1.7.0`

- **Story:** `M00-03`
- **Ecosystem:** rubygems
- **Problema resolvido:** durable asynchronous job delivery on PostgreSQL.
- **Alternativas avaliadas:** BullMQ + Redis (the specification's original text),
  Active Job's async adapter.
- **Por que não bastam:** SC-02 resolves the queue choice to Solid Queue over
  PostgreSQL; the async adapter is in-process and loses work on restart.
- **Maintenance:** maintained by the Rails core team.
- **Security:** no known advisory; runs with the application's own database
  credentials, no new network surface.
- **License:** MIT — compatible.
- **Escopo:** proportional — a queue, not a platform.
- **Impacto de longo prazo:** alto, and already accepted by the approved stack.
- **Lockfile:** `Gemfile.lock` — pinned at `1.7.0`.

## Pendências / conflitos

- **Forked workers crash on macOS.** Solid Queue's default `fork` mode segfaults
  inside libpq the moment a forked child opens a connection —
  `PG::Connection.connect_start`, before any Opanel code runs. Reproduced in a
  dozen lines with no Rails involved, against both the precompiled
  `pg-1.6.3-arm64-darwin` gem and one compiled against Homebrew's libpq, with and
  without `OBJC_DISABLE_INITIALIZE_FORK_SAFETY=YES`, and with `hostaddr` set to
  skip hostname resolution. Three strategies were tried and failed; the fourth —
  Solid Queue's `async` supervisor — works. `bin/jobs` therefore runs `async` on
  Darwin and keeps `fork` everywhere else, with the reproduction recorded in the
  script. **This is a platform incompatibility, not an Opanel defect, and it does
  not change delivery semantics.** The trade-off (no per-worker isolation on
  macOS) is recorded in the self-review and should be revisited when workers are
  actually deployed.
- **No specification conflict found.** SC-02 is applied as written.
- The recovery sweep that makes intent durable independently of the broker is
  `M01-15`. M00 proves the property the sweep will rely on: a killed job's row
  survives and re-running it converges.
