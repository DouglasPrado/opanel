## Decisões locais

- **Validation runs in `config/application.rb`, not in an initializer.** An
  initializer runs after Zeitwerk and after other initializers have already read
  configuration; by then something has already decided what to do without it. The
  file is `require_relative`'d and excluded from autoloading, because it has to
  work before Zeitwerk exists.
- **Exit code 78 (`EX_CONFIG` from sysexits(3)).** A supervisor, a runbook and
  RB-01 need to tell "the configuration is wrong" apart from "the code crashed":
  the first is fixed by an operator editing an environment, the second by an
  engineer. Exiting `1` for both loses that.
- **The message names the key and the expected shape, never the value.** A
  malformed password is still a password (Annex C §17.1). Proven by booting with
  `SECRET_KEY_BASE="short-and-secret-hunter2"` and asserting `hunter2` does not
  appear in stderr while `SECRET_KEY_BASE` does.
- **Every problem is reported at once.** Fixing one key per boot attempt is a
  waste of an operator's afternoon.
- **A default exists only where it cannot grant access.** A test iterates the
  declared keys and fails if a sensitive one ever acquires a default — so a
  default credential cannot be introduced by a later Story.
- **The guardrail checks shapes *and* destinations.** A credential shape (an AWS
  key, a private key, a JWT) is one signal; a destination is the other. A
  perfectly-shaped credential to a local database is fine and must not be flagged,
  and the same credential to `db.prod.example.com` must be. Both directions are
  tested, because a guardrail that flags everything is as useless as one that
  flags nothing.
- **`RAILS_ENV=production` is allowed.** It is a mode, not a secret, and flagging
  it would train people to ignore the guardrail.

## Acceptance Criteria

- [x] 1. Required configuration is declared in a typed, central place —
      `lib/opanel/configuration.rb`: 13 keys, each with where it is required, its
      format, its default and whether it is a credential.
- [x] 2. Boot with a missing required key aborts with a non-zero exit code naming
      the key — real subprocess, exit `78`, stderr contains `SECRET_KEY_BASE is
      required in production`.
- [x] 3. Boot with an invalid format aborts describing the expected format —
      `OPANEL_DATABASE_PORT is set but has an invalid format. Expected a
      non-negative integer.`
- [x] 4. A missing optional key uses a safe default, and no default grants access —
      development boots with nothing set; a test asserts no sensitive key has a
      default.
- [x] 5. A versioned example file lists every key with no real value — two tests
      keep `.env.example` honest in both directions, plus one asserting every
      sensitive key is empty.
- [x] 6. No development secret is versioned — `bin/workspace-guardrail` passes on
      this workspace; `config/master.key` and `config/credentials.yml.enc` were
      removed in M00-01 and the guardrail flags them if they return. The scan over
      the full branch history is M00-10's.
- [x] 7. The workspace guardrail fails on a production-credential pattern, proven
      by a negative case — six credential shapes and four destinations, each
      planted; plus six cases it must *not* flag.
- [x] 8. A configuration error does not print the received value — asserted in the
      unit specs and in a real boot.
- [x] 9. A configuration boot failure is distinguishable from any other — exit
      code 78 rather than 1, asserted explicitly.
