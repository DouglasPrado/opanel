## Findings

### F-1 — The middleware is anchored to `ActionDispatch::RequestId`

- **Dimensão:** Correção / Arquitetura
- **Severidade:** Medium (resolved)
- **Evidência:** the first attempt inserted after `ActionDispatch::Executor` and
  saw a nil request id, because the Executor runs *before* RequestId.
- **Ação:** re-anchored. Recording it because the failure was silent: logs
  appeared, correlation was simply absent, and nothing raised. A controller
  callback would have been worse — Rails logs "Started GET" and "Completed 200"
  from outside the controller, and an exception handled by the middleware stack
  never reaches one.

### F-2 — Redaction runs at the sink, not at the call site

- **Dimensão:** Segurança
- **Severidade:** Low
- **Evidência:** `Opanel::LogFormatter` applies `Opanel::Redaction` to every line.
- **Ação:** deliberate. The discipline of not logging a secret fails eventually —
  a driver interpolates a connection string into an exception, a middleware dumps
  a header — and the failure is silent. Masking at the sink costs one pass over
  each line and catches the cases nobody wrote.

### F-3 — A degraded dependency answers 503 with a classified cause

- **Dimensão:** Segurança / Operação
- **Severidade:** Low
- **Evidência:** `Opanel::DatabaseConnection` classifies into `available`,
  `authentication_failed`, `database_missing`, `host_unreachable`, `timeout`,
  `configuration_invalid`, `unknown`; `/up` reports the class and nothing else.
- **Ação:** deliberate on both sides. A generic timeout sends an operator to the
  wrong system; a connection string in the response would publish a credential to
  anything that can reach the panel. The classification is the middle ground, and
  a test asserts no version, hostname or connection string appears.
