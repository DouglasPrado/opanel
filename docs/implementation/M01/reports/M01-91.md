## Por que cada spec estava vermelho sob `--parallel`, com evidência

`bin/test --parallel` was reported to leave five examples red. Reproduced
directly (running just the three/four affected files together, `--parallel`,
repeatedly) rather than assumed:

1. **`spec/security/security_scan_spec.rb`, "passes on this repository, tree
   and history"** — `bin/security --fast --history` (`gitleaks dir .`) scans
   every file physically on disk. `spec/gates/gate_scripts_spec.rb` and
   `spec/gates/ci_pipeline_spec.rb` briefly write a real, secret-shaped probe
   into the *same* working tree (`with_staged`/`with_probe`) to prove the
   staged-secret check rejects it. Under `--parallel` those run in different
   worker processes at the same instant. Reproduced deterministically (3/3
   attempts) with:
   ```
   bin/test --parallel spec/gates/gate_scripts_spec.rb spec/gates/ci_pipeline_spec.rb \
     spec/security/security_scan_spec.rb
   ```
   `secret-scan FAIL ... leaks found: 1` — a leak neither the scan's own
   examples nor "passes on this repository" planted.

2. **`spec/security/production_logging_spec.rb`, 4-5 of its 6 examples** —
   `config.eager_load = true` in production makes Zeitwerk `require` every
   file under every autoload path, including `lib/opanel/`, where
   `ci_pipeline_spec.rb`'s "blocks a lint error" plants a deliberately
   malformed probe (`lib/opanel/ci_probe_broken.rb`, intentionally not
   defining `Opanel::CiProbeBroken`). If that probe is on disk the instant
   another worker boots production, Zeitwerk raises
   `Zeitwerk::NameError: expected file ... to define constant
   Opanel::CiProbeBroken, but didn't` — a boot failure with nothing to do
   with logging. Reproduced intermittently (2 of the first 3 attempts) before
   the fix; the first bootsnap-cache-dir hypothesis I tried did not touch the
   real cause and was reverted once the actual `Zeitwerk::NameError` was
   captured (`/tmp/repro_1.log`, kept only as local scratch evidence during
   the investigation, not committed).

The fix is the same for both: a `flock`-based advisory lock
(`spec/support/repository_lock.rb`) taken by every example that mutates the
tracked tree (`with_staged`, `with_probe`) and by every example that reads
*all* of it at once (`security_scan_spec.rb`'s two tree-wide examples,
`production_logging_spec.rb`'s `boot_production`). `TEST_ENV_NUMBER`-style
per-worker namespacing (the pattern in `spec/support/concurrency.rb`) cannot
isolate this class of race: the contended resource is the one checkout every
worker shares, not a name a worker can pick for itself.

A single exclusive lock (not a read/write split) is deliberate. A read/write
attempt (probes take a shared lock, tree-readers take exclusive) was tried
and reverted: `git add`/`git rm --cached` both take `.git/index.lock` and do
not retry on contention, so two probes running concurrently under a shared
lock intermittently made one of them silently no-op — reproduced as
`spec/gates/gate_scripts_spec.rb`'s "rejects a staged build artifact"
expecting `fail`, getting `pass`, because the probe file was never actually
staged. Every writer and every whole-tree reader now takes the one lock.

**Verification, after the fix — repeated runs, not a single green:**

```
bin/test --parallel spec/gates/gate_scripts_spec.rb spec/gates/ci_pipeline_spec.rb \
  spec/security/security_scan_spec.rb spec/security/production_logging_spec.rb \

```
Run 9 times after the fix (across the read/write attempt's revert and the
final version): 0 failures every time, 169 examples each run.

```

```
Run twice: 730 examples, 1 failure both times — `spec/gates/pack_spec.rb`
("validates every Milestone of this repository"), which is **not** related to
this Story (see Pendências) and reproduces identically serially, single-file,
with no concurrency involved at all.

## Scope verification (per the Goal's instruction, before touching anything)

**Scope item 1 — "prove the gates against a fixture repository, not this
one."** Verified against current code rather than assumed. Neither
`spec/gates/gate_scripts_spec.rb` nor `spec/gates/ci_pipeline_spec.rb` calls
the full `bin/gate local` or `bin/gate pre-commit` from inside an example
today (`grep -n 'gate(\|gate_json(' spec/gates/*.rb` — the only
`local`/`pre-commit` calls are `gate_json("pre-commit", "--only",
"no-stray-files", ...)`, which is `--only`-narrowed). That is the actual
defect the Story opens with — "one of them is `bin/gate` itself, which runs
`bin/test`, which runs the suite again" — and it is already gone, delivered
in `70c7f7e`/`3d05b73` before this Story reached the loop, via `--only`
narrowing rather than a literal fixture-in-`tmp/` repository. I did not
rebuild it as a fixture: the stated purpose (proving a gate without paying
for a re-entrant full suite) is already met, and `spec/gates/gate_budget_spec.rb`
now adds a permanent, static regression guard against it coming back
(see AC4). Not redone, per "if 70c7f7e already satisfies an item, say so with
evidence and do not redo it."

**Scope item 3 — "scope the secret scan by gate."** Partially verified as
already done, partially found still open. `bin/security` itself (unmodified
by this Story) already documents and implements the three scopes explicitly
in its own header and at each `gitleaks` invocation: `--fast` (secret scan
only), `--staged` (the git-staged diff — what `pre-commit` calls), `--history`
(adds the commit history — what CI's `security-fast` job exercises via
`spec/security/security_scan_spec.rb`'s own "passes on this repository, tree
and history"). That satisfies AC6 as written ("explicit and documented in
`bin/security`; the full tree-and-history scan still runs in CI").

What is **not** done, found by measuring rather than assuming: `bin/gate
local`'s own stanza calls `bin/security --fast` with no `--staged`, so
`local` still scans the *whole tree* (`gitleaks dir .`), not "the diff" the
Scope item asks for. Measured directly: `bin/security --fast` took `36976ms`
on an unmodified run (`waivers 85ms`, `allowlist 44ms`, `secret-scan
36708ms`). Wiring `local` to a diff-scoped invocation needs the same one line
in `bin/gate` that AC5 needs, and is blocked by the same deny. Recorded
honestly here rather than claimed as done.

## Pendências / conflitos

- **`bin/gate` could not be edited.** Attempted twice (`Edit` tool), both
  denied with: *"This is a quality gate. Failing a gate means fixing the
  implementation — a gate edited to pass protects nothing."* Per the Goal's
  explicit instruction, no workaround was attempted (no `Write`, no shell
  rewrite, no hook bypass, no `--no-verify`). This blocks AC1 and AC5
  directly, and Scope item 3's `local`-specific diff-scoping indirectly. The
  one remaining change is exactly two lines in `bin/gate`'s `local` case:
  `bin/test --changed` → `bin/test --changed --parallel`, and its adjoining
  comment (already partly rewritten in the Story file's own "Já entregue"
  section) needs to say the fix landed rather than that it is still owed.
- **`spec/gates/pack_spec.rb` fails independently of this Story.** Confirmed
  by running it alone (`bundle exec rspec spec/gates/pack_spec.rb -e "validates
  every Milestone"` → fails identically, serially, no concurrency involved):
  `docs/implementation/M01/tasks.json` carries a `run` key
  (`{"startedAt": ..., "turns": 0, "doneAtStart": 1}`) that
  `config/pack/tasks.schema.json` does not allow. That file is orchestrator
  state (the loop's own run-tracking, written before this session started),
  not part of M01-91's declared boundary (`bin/gate`, `bin/security`,
  `bin/test`, `spec/gates/**`, the two named security specs,
  `spec/spec_helper.rb`, `spec/support/**` — `docs/implementation/M01/tasks.json`
  and `config/pack/` are not in it), and per instruction ("Do not touch
  `tasks.json`") was left untouched. Flagging it here rather than fixing it
  silently or leaving it unexplained in a red `tests` check.
- **The `--parallel` speedup is smaller than the Story's own "already
  delivered" measurement assumed**, once correctness is accounted for. The
  Story's "Já entregue" section reports "leva a suíte de 193s para 88s" for
  `--parallel`, measured before the five collisions were root-caused. With
  the mutual-exclusion fix in place (necessary — a faster gate that reports a
  false failure is worse than a slow one), the four affected files together
  cost ~140-146s under `--parallel`, not 88s, because
  `security_scan_spec.rb`'s own ~85s full-tree scan cannot safely overlap any
  of the others. A deeper fix — scanning a git worktree/snapshot instead of
  the live checkout, so a full-tree scan cannot be disturbed by a concurrent
  probe at all — would remove the need for mutual exclusion and likely
  recover most of the gap, but is a heavier redesign of
  `security_scan_spec.rb`'s two examples than "smallest complete solution"
  for this Story, and is left as a candidate for a follow-up Story rather
  than attempted here.
- None of the above required weakening, skipping, tagging out or removing
  any check or assertion. Every negative case `spec/gates/` and
  `spec/security/` had before this Story still fails what it targets
  (AC3, evidenced above).
