## Decisiones locales

1. **Lock signature**: Used `result.value` directly (ResourceLock object) not `result.value[:lock]` (hash). AcquireResourceLock returns `Opanel::Result.success(lock)`.

2. **Resource ID for networks**: Networks identified by `environment_id` in executor, not `network_id`, because:
   - One network per Environment (unique constraint)
   - find_by_label("/networks", resource_id) searches by "com.opanel.environment_id" label
   - So ExecutorCommand must use environment.id as resource_id

3. **RequestContext → Current**: Commands run outside HTTP context; used `Current.correlation_id.presence || SecureRandom.uuid`.

4. **ExecutorCommand construction**: Networks require proper ExecutorCommand structure with type, cluster_id, resource_type, resource_id, payload (name, labels, attachable). Executor validates payload keys against allowlist per type.

5. **NetworkPolicy rewrite**: Changed to ApplicationPolicy pattern with PERMISSIONS map, matching ServicePolicy architecture.

## BLOCKED — arbiter decision of 2026-09-11

`M01-17` is **blocked**, not done. Five Swarm examples are red and the criteria
they prove — AC1, AC2, AC3, AC4, AC5, AC6, AC8, AC11 — are **not** satisfied.
None of them is ticked above on the strength of a test that failed.

The arbiter's diagnosis, recorded verbatim from
`docs/implementation/M01/DECISIONS.md`:

- `app/reconcilers/network_reconciler.rb:112,176` — the UUID lead is **not** the
  cause. `ExecutorCommand#id` is never validated: `swarm_executor.rb:274-279`'s
  `identifier` helper is applied only to `command.resource_id`, which carries a
  bare 26-char ULID and matches `ExecutorCommand::RUNTIME_IDENTIFIER`. A fifth
  round aimed at the UUID would not move an assertion. It is a real ADR-0002
  inconsistency and nothing more.
- `app/reconcilers/network_reconciler.rb:126,128` read
  `result.safe_metadata.dig(:network_data)`. `swarm_executor.rb:169-175`
  (`do_inspect_network`) returns `ExecutionResult.applied(command, ids:, name:,
  driver:)`; `app/executors/execution_result.rb:61-64` carries no such key.
  `actual` is therefore nil on every path, always.
- `swarm_executor.rb:170` addresses the network as
  `GET /networks/<environment ULID>` — `resource_id` is
  `network.environment.id`, which is neither a Docker network id nor its name.
  The inspect 404s regardless of what the daemon holds.
- `lib/opanel/ownership.rb:119` reads `dig("Spec","Labels")` — the Swarm
  *service* shape. `GET /networks/{id}` returns `Labels` at the top level, so
  `managed_by_platform?` answers `false` for every network the platform itself
  creates, which is precisely the gate at `network_reconciler.rb:201` that would
  mark `READY` and advance `applied_revision`.

### What the owner has to decide

One question, and it needs an ADR: **how the Swarm Executor returns an observed
resource body to a reconciler.** `ExecutionResult` has no field for one, and
`safe_metadata` is the bag `swarm_executor.rb:402-418` writes into the forensic
log line — which that method's own contract says never carries a body. Until
that contract exists there is no correct place for `inspect_network` to put the
JSON the reconciler must read, and no bounded fix round can invent one: a
contract change between modules is an ADR, not an edit.

### Consequence

`M01-18` through `M01-23` all depend on `M01-17` and are not started. M01 halts
here. The four Stories completed in this run — `M01-14`, `M01-15`, `M01-16` and,
before them, `M01-13` — are committed, reviewed and green.

### One finding that reaches back

`Opanel::Ownership.managed_by_platform?` cannot recognise a network, and
`M01-16` shipped with three green unit specs covering it. Those specs build
their fixtures in the service shape, so the predicate is green against a
fiction. That is a defect in committed, reviewed work and it belongs with the
executor-observation ADR rather than with this Story.
