## Database Schema

- Table: `environments` with columns:
  - id, project_id, cluster_id, team_id (FK, NOT NULL)
  - name, slug (unique per project when not deleted)
  - type (PRODUCTION | HOMOLOGATION | DEVELOPMENT | PREVIEW | CUSTOM)
  - auto_promote_secrets (defaults false, forbidden true in PRODUCTION)
  - status (PROVISIONING | READY | DEGRADED | PAUSED | DELETING)
  - desired_revision, applied_revision (null until reconciler runs at M01-18)
  - Timestamps: created_at, updated_at, deleted_at
  
- Constraints:
  - Partial unique index on (project_id, slug) where deleted_at IS NULL (AC2)
  - Check constraints on ULID formats, slug format, type, status, revisions
  - Foreign keys to projects, clusters, teams with ON DELETE RESTRICT

- Indices:
  - (project_id, slug) unique where deleted_at IS NULL
  - (project_id, id) for keyset pagination
  - (cluster_id) for efficient queries through cluster
  - (team_id) for tenant scoping

## Implementation Notes

### Why no `class Environment < ApplicationRecord` method to authorize creation?

The Story's spec declares `Policies: criar exige ADMIN`. This is a Team-level permission (the same row as Project creation). Rather than create an unsaved Environment stub, the Command could have authorized on the Project with a `:create` action. However, `EnvironmentPolicy` is the entity's natural home and was declared critical (AF-07), so authorization flows through it with the temporary instance pattern used in `BootstrapCluster`.

### Tenant scope via denormalized team_id

`Environment.team_id` is denormalized from `project.team_id` to avoid a join in `TenantScope.accessible_to`. This improves query efficiency and maintains the tenant boundary at the model layer.

### Migration index safety

All four indices on the new `environments` table carry `migration-index-review: new empty table` comments as per the M01-08 pattern, since the table is created empty and the index build is instantaneous without needing concurrent building.

## Fix Round 3: Flaky Keyset Pagination Index Test

**Problem:** The test `environment_constraints_spec.rb:185` ("reaches a page through index_environments_on_project_id_and_id") was order-dependent — it passed when run in isolation but failed when run with other specs due to the query planner choosing `environments_pkey` instead of the composite index `index_environments_on_project_id_and_id`.

**Root Cause:** With only 3 rows all in the same project, the PostgreSQL planner legitimately chose to walk the primary key and filter by project_id, which is a valid and cheap plan. The test assertion pinned a planner *choice*, not a database correctness guarantee.

**Solution:** Made the composite index genuinely the better plan by creating enough rows across multiple projects and running ANALYZE:

1. Created 3 additional projects with 5 environments each (15 rows in other projects)
2. Created 3 environments in the target project
3. Executed `ANALYZE environments` so the planner has accurate row count statistics
4. With this distribution, walking the primary key would be expensive (must read/discard 15+ rows from other projects), making the composite index preferable

**Verification:**
