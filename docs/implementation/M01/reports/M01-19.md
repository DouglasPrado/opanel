## Architecture & Implementation Notes

### Design Decisions

**1. ServiceObservation Model**
- Append-only, immutable record of observed state at a point in time
- Never writes desired-state columns (team_id, service_id, etc. for identity only)
- Separate from Service desired state (doc 09 §10)

**2. Status Derivation**
- `Opanel::ServiceStatus.derive(applied_revision:, desired_revision:, observation:)` computes status
- No `services.status` column write from reconciliation
- Status enum: `PENDING`, `DEPLOYING`, `HEALTHY`, `DEGRADED`, `FAILED`, `PAUSED` (doc 07 §17.1)
- Stale observations never report `HEALTHY`

**3. ObserveService Command**
- Reads actual state via SwarmExecutor `inspect_service` + `list_tasks`
- Returns observation data hash to be persisted
- Accepts optional `executor` param for testability
- Rejection of out-of-order observations (lower `docker_version_index` than latest) prevents stale data overwriting newer observations

**4. Docker Version Tracking**
- `docker_version_index` from `docker service inspect` `Version.Index` field
- Used to detect observation ordering violations
- Increments on every Swarm state change (replica count, image, labels, etc.)

**5. Stale Data Handling**
- `observed_at` timestamp always present
- `Opanel::ServiceStatus.stale?(observation, current_time)` checks threshold (5 minutes)
- Stale observations cannot contribute to `HEALTHY` status
- UI shows "last observed X minutes ago" when stale

### Known Debt & Handoff

**M02-04:** Health check configuration (probe policy, manual health status). Currently all running tasks count as healthy.

**M02-05:** Crash loop detection. Not included in M01 observation.

**M02-06:** DRIFTED status (when actual diverges from desired in harmful way). M01 observes divergence but doesn't act on it.

**M02-12:** Docker Events accelerator. M01 uses periodic sweep only.

**M01-18 Inherited Debt — `Version.Index` Ordering:**
The `current_tasks` filter in SwarmExecutor uses slot + highest Version.Index to exclude historical tasks. This is sound for individual tasks, but the assumption that Version.Index strictly increases with every Swarm state change was not formally proved in M01-18. ObserveService inherits this pattern and applies it at observation level:
- Observation A with `docker_version_index=100` is newer than observation B with index=50
- If B arrives after A, it is rejected

This is correct if Swarm's Version.Index is monotonic per service. No evidence of it regressing was found in testing.
