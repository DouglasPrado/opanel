## Findings

### F-1 — AC1 and AC5 unmet: `bin/gate local` still runs the unmodified path, and would still miss the 90s ceiling if unblocked

- **Dimensão:** Correção / Testes
- **Severidade:** Critical
- **Evidência:** `bin/gate:179` still reads `gate_run "tests" bin/test --changed` (confirmed: `git diff HEAD -- bin/gate` is empty — the file is byte-identical to `HEAD`). The report's own manual run (`docs/implementation/M01/reports/M01-91.md`, "Testes executados" table) measures `bin/gate local --format json` at `242493ms` total, `tests FAIL 195907ms` — far over the 90s ceiling the Story requires.

  This is not only a permissions problem. Even setting the denied edit aside, the report's own number for the fixed, `--parallel`-run subset of the previously-red files (`spec/gates/gate_scripts_spec.rb`, `spec/gates/ci_pipeline_spec.rb`, `spec/security/security_scan_spec.rb`, `spec/security/production_logging_spec.rb`, `spec/gates/gate_budget_spec.rb`) is "~140-146s," not the "88s" the Story's own "Já entregue" section assumed. I reproduced this independently, twice: `bin/test --parallel <those five files>` finished in `145.4s` and `142.9s` respectively, both `169 examples, 0 failures`. `security_scan_spec.rb`'s own full-tree scan alone costs ~85s and, by the correctness fix in this diff, can no longer overlap with anything that stages a probe — so it sits on the critical path. `tests` alone would therefore still exceed the 90s total gate budget even with the one-line wiring applied, before `format`/`lint`/`typecheck`/`security`/etc. add their ~11s.
- **Ação:** none taken; correctly reported as `partial` in the report's own "Resultado" section, but the per-AC checklist for AC1 (see F-4) obscures this.
- **Estado:** open — blocks DONE. Unblocking the `bin/gate` edit is necessary but, per the measurement above, not sufficient: the 90s ceiling needs either a further reduction in the serialized full-tree-scan window or a redesign of how `security_scan_spec.rb` claims exclusivity (the report itself names a worktree/snapshot approach as a candidate, left for a follow-up).

### F-2 — The AC7 "budget" spec cannot catch the regression it is supposed to catch

- **Dimensão:** Testes / Observabilidade
- **Severidade:** High
- **Evidência:** `spec/gates/gate_budget_spec.rb:37-74`. The three `diagnose` examples ("says nothing is wrong…", "names the check that broke the budget…", "picks the single worst offender…") call the diagnosis helper only against hand-built hashes (`within_budget`, `over_budget`) — never against a real `bin/gate local --format json` run. The only thing that touches the live gate at all is the separate static regex in the same file (`gate_budget_spec.rb:82-107`), which detects one specific historical cause (an unrestricted `gate("local"|"pre-commit")` call from inside a spec) and nothing else.

  The Story's own Failure Scenario table asks for: "A future Story re-introduces recursion → the budget spec goes red, with the check named" and Required Tests lists "budget: the local gate under its ceiling." Neither is met by code that can fail only on synthetic input. A regression that keeps the suite fast on `--changed` selection but silently drops `--parallel` from `bin/gate`'s `local` case (exactly what is true in the tree today), or that lets `tests`/`security` grow past budget through means other than re-entrancy, produces no red anywhere in this diff — the exact "assertion that cannot fail [against the thing it claims to protect]" pattern Annex I §17.1 flags as the most important class of finding. The report itself concedes this at `docs/implementation/M01/reports/M01-91.md:184`: "The live number (AC1) is recorded here rather than asserted automatically."
- **Ação:** none taken; disclosed as a deliberate trade-off in the report, but the trade-off leaves AC7 substantively unmet, not merely partially automated.
- **Estado:** open — blocks DONE (missing test for a stated Acceptance Criterion).

### F-3 — Required Test "one rspec process per gate run" (AC4) has no automated check

- **Dimensão:** Testes
- **Severidade:** High
- **Evidência:** The Story's Required Tests section lists "integration: one rspec process per gate run" as its own class, distinct from the static re-entrancy grep. ### F-5 — The single global `flock` is correct today but is already the new bottleneck the Story exists to remove

- **Dimensão:** Simplicidade / Concorrência
- **Severidade:** Medium
- **Evidência:** `spec/support/repository_lock.rb` uses one exclusive lock for every writer and every whole-tree reader, by design (a read/write split was tried and reverted — documented in the report — because `git add`/`git rm --cached` contend on `.git/index.lock` and don't retry). This is the right correctness call for what exists today: verified independently, `bin/test --parallel` on the five affected files passed twice in a row (169 examples, 0 failures each time, no flake, no deadlock). But it is coarse-grained: `security_scan_spec.rb`'s own ~85s full-tree scan now serializes against every probe-planting example in `spec/gates/*`, which is most of what made "Já entregue"'s 88s estimate optimistic (measured 140-146s instead, per F-1). As more `:slow` suites gain `--parallel` in later work, this single lock is the thing that will keep the ceiling from moving further down, and nothing currently measures or alerts on that growth (only the header comment in `repository_lock.rb` explains the trade-off).
- **Ação:** none taken; the report names a candidate fix (git worktree/snapshot scanning) as future work, which is the right scope call for this Story rather than doing it here.
- **Estado:** open, informational — not itself blocking, but relevant to whoever picks up the 90s target next.
