## Criticals — both closed

### C-1 — closed. I could not get any value through.

**Fix:** `app/audit/audit_sanitizer.rb:106-113`. `scalar`'s `else` branch is now
`OMITTED` (`:30`) instead of `value.to_s`. Symbols are converted explicitly at
`:109`, so the one legitimate non-String scalar did not become collateral.

I re-ran the round-1 probe and then went further — seventeen shapes, every one
designed to get a planted marker past the allowlist:

```
nested hash                              leak=false  {"name" => "[OMITTED]"}
array                                    leak=false  {"status" => "[OMITTED]"}
symbol key with nested hash              leak=false  {"name" => "[OMITTED]"}
custom to_s object                       leak=false  {"name" => "[OMITTED]"}
HashWithIndifferentAccess (nested)       leak=false  {"name" => "[OMITTED]"}
HashWithIndifferentAccess (sensitive)    leak=false  {"password_digest" => "[CHANGED]"}
"Password" (capitalised)                 leak=false  {}
"authToken" (camelCase)                  leak=false  {}
"PASSWORD" (upper)                       leak=false  {}
" password " (padded)                    leak=false  {}
3 levels deep under an allowed key       leak=false  {"name" => "[OMITTED]"}
Struct                                   leak=false  {"name" => "[OMITTED]"}
Set                                      leak=false  {"status" => "[OMITTED]"}
sensitive key holding a nested hash      leak=false  {"password" => "[CHANGED]"}
```

The case-variant keys (`Password`, `authToken`, `PASSWORD`) are worth naming: they
are **dropped**, not masked, because they are on no allowlist. That is the allowlist
doing the work a blocklist could not — a blocklist keyed on `password` would have
recorded all three. This is the property the Story asked for, demonstrated.

Then end to end, through the real writers, planting into **both** `before` and
`after` and through the denial path, sweeping every column of every row:

```
ROWS: 7
PLANTED SECRET ANYWHERE IN audit_logs?  false
RAW PASSWORD ANYWHERE?                  false
PASSWORD DIGEST ANYWHERE?               false
TOKEN DIGEST ANYWHERE?                  false
RAW TOKEN ANYWHERE?                     false

team.created          before={"name" => "[OMITTED]", "slug" => "[OMITTED]"} after={"status" => "[OMITTED]"}
user.registered       before={"display_name" => "[OMITTED]"}                after={"password" => "[CHANGED]"}
session.revoked       before={}                                             after={"mfa_level" => "[OMITTED]"}
authorization.denied  before={}                                             after={"reason" => "no_membership"}
```

Two values *do* survive: a plain String under `Team#name` and under
`User#display_name`. That is not a leak — those keys are on the allowlist by an
explicit reviewed line, and a user typing a secret into their own display name is
their string, recorded because the trail is supposed to record it. A `String`
subclass behaves identically, correctly.

`OMITTED` rather than dropping the key is the right call and the class comment says
why: "the field was empty" and "the field carried something we would not store" must
not read the same to an operator.

## Highs — all four closed

### H-1 — closed. The examples now assert the value, not the type.

`spec/unit/audit_sanitizer_spec.rb:60-101`. Every assertion in the nested-value block
names the planted marker (`expect(result.to_json).not_to include("PLANTED-hunter2")`)
and pins `result["name"]` to `OMITTED`. Two examples were added for the shapes I used
in the attack — an Array holding a Hash, and an object whose `to_s` would have
rendered — plus a symbol-key example. The comment records why `be_a(String)` was the
wrong assertion, which is the part that stops it recurring.

### H-2 — closed, and better than asked.

`spec/integration/audit_log_append_only_spec.rb:84-142`. The scan is now
`rewrites_the_trail(sources)`, a method both examples drive, so the control can no
longer pass against a copy. Three things I checked specifically:

- **Scope widened to `lib/opanel/**`** (`:100`), and there is an explicit assertion
  that `lib/opanel/authorization.rb` is among the files read (`:109-110`) with the
  message "the scan is not reading the audit writers it is meant to cover". That is
  the gap I reported, closed at the right layer.
- **A raw-SQL pattern was added** (`UPDATE audit_logs|DELETE FROM audit_logs`), which
  catches the `connection.execute` shape the old regex missed.
- **A negative control** (`:135-142`) asserts ordinary code — `AuditLog.create!`,
  `AuditLog.for_request` — is not reported, so the scan cannot pass by matching
  everything.

The planted-source example deliberately does **not** claim `d.rb`
(`entry.update_columns(...) # audit_logs`) is caught, and says so in a comment. A
rewrite through a variable named something other than `audit_log` still escapes. That
is inherent to a regex scan, it is now disclosed in the spec itself rather than
implied away, and I am not reopening it.

### H-3 — closed. The exemption was reverted, and AF-06 still sees the file.

This is the finding I asked the lead to defend, and he reverted instead. Verified:

- `config/architecture/fitness.yml` is **unmodified by this Story** (`git diff --stat`
  on it is empty). `fitness_self_referential` is back to its three original entries;
  `waivers` is still `[]`.
- `bin/fitness` PASS with no exemption and no waiver.
- The sensitive list is now two lines carrying `# REDACTED: named here to be refused`,
  which is AF-06's own line-scoped escape (`lib/gates/fitness_functions.rb:256`) used
  as designed.

**The lead's question — did he trade an explicit exemption for an implicit one?**
I tested it directly, by running AF-06 against a copy of the file with a leak planted
elsewhere in it:

```
1. unmodified copy of audit_sanitizer.rb          violations: 0
2. same file + Rails.logger.info(password: ...)   violations: 2
     app/audit/audit_sanitizer.rb:60  reaches a serializer or audit payload
     app/audit/audit_sanitizer.rb:60  reaches a log, error or render sink
3. same leak with a `# REDACTED` comment on it    violations: 0
```

**No.** Result 2 is the answer: the file is fully scanned again, and a real leak in it
is caught by both halves of AF-06. The whole-file blind spot is gone.

Result 3 is worth stating but is not this Story's defect: any line can silence AF-06
by containing the word "REDACT", because `REDACTING` is a line-level regex that
predates this Story. That is a weakness of the checker in `lib/gates/`, which M01-05
may not touch and M01-91 owns. Recorded as L-3 so it is not lost. Compared to the
whole-file entry — permanent, invisible from the file, no approval, covering every
future line — a two-line marker visible at the point of use is strictly the better
instrument, and it is the one AF-06 was built with.

### H-4 — closed.

`spec/unit/audit_actions_spec.rb` exists (91 lines). The list is transcribed by hand
into `EXPECTED` and compared with `eq`, which is the right construction: a spec that
iterates the constant it checks proves the constant equals itself. It also asserts

than being written under a made-up name, and — usefully — that

## Open — Medium

### M-2 — `record_denial` is not outside the caller's transaction, and the comment says it is

**File:** `lib/opanel/authorization.rb:84-87`. Unchanged this round.

The comment claims *"Written outside any transaction the caller may hold."* The method
opens no transaction, so it joins whichever one is open. Verified in round 1: a denial
raised inside a caller transaction that rolls back is rolled back with it
(`DENIAL SURVIVES CALLER ROLLBACK? false`).

**Judging the justification, as asked.** The *design intent* — do not couple a denial's
record to a mutation's rollback, because a denial mutates nothing — is sound, and it is
the right call for the only current call site
(`app/commands/suspend_team_member.rb:99`, outside the transaction). What does not hold
is the sentence describing it: the code delivers the intent by accident of where it is
called from, not by construction, and it tells the next author a guarantee it does not
provide. The first Command that authorizes inside its transaction loses the denial
silently — and after C-2 every Command in this Milestone now runs its work inside a
transaction, so that call site is closer than it was. Either open a separate connection
/ `after_commit`-style path and keep the comment, or change the comment to describe
what the code does.

### M-3 — a failed denial-audit turns a 403 into a 500

**File:** `lib/opanel/authorization.rb:89`, unrescued `create!`. Unchanged.

The same comment says losing the request "would turn an audit problem into an outage";
the code produces exactly that (verified round 1:
`DENIAL PATH RAISED ActiveRecord::StatementInvalid -- a 403 becomes a 500`). Whichever
behaviour is intended — fail closed on the audit, or degrade and surface the
degradation per Annex I §19.2 — code and comment currently disagree and neither is
tested.

### M-4 — append-only is weaker than the model and the report claim

**File:** `app/models/audit_log.rb:61-69`. Unchanged.

`update`, `update!`, `destroy`, `destroy!` are overridden and `readonly?` blocks
`save`/`update_columns`. Verified in round 1 that three ordinary Active Record paths
still succeed: `record.delete`, `AuditLog.delete_all`, and `AuditLog.update_all` — the
last rewrites a persisted row without touching `revision`, so `CHECK (revision = 1)`
never sees it.

New this round: the M-6 fix makes two spec files *depend* on `delete_all` working
(`AuditLog.where(actor_id: users).delete_all`). That is legitimate — test cleanup must
be able to do it — but it means hardening the model later now has a caller to
accommodate, and it should be recorded before somebody discovers it the hard way.

The Story's other half of the guarantee — *"permissão de banco"* — is still absent,
dismissed in the migration comment as an operational concern with no backlog entry or
runbook note that I could find.

### M-5 — `authorization_denied` in `INSTANCE_ACTIONS` still deviates from the Story's tenancy rule

**File:** `app/models/audit_log.rb:35-48`. Unchanged.

Story Domain Impact: *"`teamId` nulo é permitido **somente** para eventos de
instalação"*; `authorization.denied` is not one. The engineering reason is sound, but
it is a deviation from an approved Story rule decided in code rather than recorded per
"Specification Conflicts", and it removes tenant-scoped denials from the AC10 sweep at
`spec/integration/audit_trail_spec.rb:189-190`.

Partly mitigated this round: `spec/unit/audit_actions_spec.rb:81-89` now asserts that
`INSTANCE_ACTIONS` excludes every Team-scoped action, so the list cannot grow to
swallow `team.created`. The narrower construction — allow a null Team only when
`result == "DENIED"` — would close it entirely.

### M-7 — the report contradicts itself about what was decided

**File:** `docs/implementation/M01/reports/M01-05.md`.

The "Correção da revisão" section (from `:143`) is accurate, specific and honest. The

- `:23-25` — *"**Valor aninhado é achatado** ... levaria a senha sob uma chave

## Open — Low

### L-1 — the AC3 examples still bind to an arbitrary row

`spec/integration/audit_trail_spec.rb:17, 28, 66` still use
`AuditLog.find_by(action: ...)`, which returns any matching row. Correct today because
the leakage cause is fixed and these run transactionally, but the next non-transactional
spec that writes audit reintroduces it. The right pattern is in the same file at `:55`

`app/audit/audit_trail.rb:43`, `lib/opanel/authorization.rb:96`. At an HTTP boundary
`Opanel::CorrelationMiddleware` sets both, so AC7 is genuinely met. Outside a request
both columns receive the same generated UUID and a reader cannot tell a real request id
from a synthesised one.

### L-3 — AF-06 can be silenced by writing `REDACT` on the leaking line

`lib/gates/fitness_functions.rb:256`. Demonstrated above (result 3). Pre-existing, not
introduced by this Story, and outside its boundary — `lib/gates/**` belongs to M01-91.
Recorded so it reaches the Story that owns the gates.

### L-4 — the AC8 chain is AuditLog-only

`operation_id` exists and is `nil` on every row this Milestone writes; the Operation
Engine is a later Story. The half that can exist does exist and is indexed.
