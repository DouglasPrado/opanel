## Findings

### F-1 (High) — `blocking_code` reads task *history*, so a Service can never leave BLOCKED, and a converged pass can be flipped to BLOCKED by a dead task

`app/executors/swarm_executor.rb:280-295,307-317` filters `/tasks?filters={"service":[id]}` and `blocking_code` scans **every** returned task for a non-empty `Status.Err`, with no filter on `DesiredState`, on task state, or on the task's slot/revision. Swarm keeps terminated tasks (`task-history-limit`, default 5). `app/reconcilers/service_reconciler.rb:332-337` calls it on the NOOP path (`:360-361`) and on the verify path (`:309-310`).

Consequence, using this Story's own scenario: `service_blocked_lab_spec.rb:35-52` leaves a `Rejected` task carrying "failed to resolve reference … not found". The operator then fixes the digest. The next pass applies, re-inspects, `converged_on?` passes — and `blocking_code` still matches the *historical* task, so `verify` calls `blocked`, the Service is set `DEGRADED` and the Operation `FAILED` on a deploy that actually succeeded. The same shape flips a healthy NOOP pass to BLOCKED. That is a degraded state reported for a healthy runtime and a reconciler that cannot converge out of it until task history rolls over.

No test covers recovery from BLOCKED: every example in `service_blocked_lab_spec.rb` asserts entry into BLOCKED and stops. AC4 (second run is NOOP) and AC9 (blocked "until the image is available") are therefore unverified in the one sequence where they interact. This is a High: a missing test over a real convergence defect, and it blocks DONE.

### F-2 (Medium) — `ReconciliationRun.result` is written `SUCCESS` before anything is applied

`app/reconcilers/service_reconciler.rb:201-210` creates the run with `result: provisional_result(diff)` and `:489-491` returns `SUCCESS` for every non-BLOCKED class. A worker that dies between the create and `verify` — precisely AC7's scenario, exercised in `spec/integration/service_restart_lab_spec.rb:14-18` — leaves a persisted `ReconciliationRun` claiming `SUCCESS` for a pass that did not converge. AC13 asks the run to carry the *result*; a provisional optimistic result is the "stored boolean that is not derived" failure mode in a different place. The restart spec asserts the database "knows nothing" (`:32-33`) but never asserts on the abandoned run's result, so the lie is untested.

### F-3 (Medium) — two exits leave the Operation stuck in `RUNNING`

`app/reconcilers/service_reconciler.rb:386-392` (`failure`) drives no Operation state, and it is the exit for `verify`'s "the runtime did not confirm" (`:305-307`) and for an Engine rejection (`:267-270`). `:174-179` likewise returns `Opanel::Result.success(converged: false)` after `MAX_CONVERGENCE_PASSES` with the Operation still `RUNNING` — and reports a non-convergent pass as `success`. `start_operation` has already moved it to `RUNNING` at `:253-254`, so the row is left non-terminal with a released lease, depending entirely on M01-14's stalled sweep to notice. The Story's Async section requires the Operation to reach a terminal state; the two BLOCKED/SUCCEEDED paths do so and these two do not.

### F-4 (Medium) — the supersession and applied-revision unit evidence cannot fail on `converged_on?`

`spec/support/fake_swarm_executor.rb:60-75` builds the observation **from Desired State** (`image_for(service)`, `service.replicas`, `labels_for(service)`), and `spec/unit/service_supersession_spec.rb:74,94,113` passes `service.reload`. So `converged_on?` (`service_reconciler.rb:321-327`) is true by construction in every one of those examples; the AC10 guard they exercise cannot fail. The real proof of AC10 is the lab spec (`service_lost_response_lab_spec.rb:34-35`), which is why this is Medium and not High — but it is the permissive-stub class this ledger already recorded at `DECISIONS.md:375`, recurring. An example that returns an observation whose image or replicas disagree, and asserts `applied_revision` does **not** advance, is missing.

### F-5 (Medium) — `verify` confirms image and replicas but not the revision label the diff decides NOOP from

`service_reconciler.rb:321-327` compares `attributes["image"]` and `attributes["replicas"]`; `service_diff.rb:142-145` decides NOOP from `com.opanel.desired_revision`. The two do not use the same evidence, so a pass whose only change was invisible (resources, placement, healthcheck, args) can advance `applied_revision` on an observation whose label still names the old revision — and the next pass then re-classifies `ROLLOUT` forever. The builder's own argument at `service_diff.rb:26-29` is the reason the label matters; `converged_on?` should assert it. Today nothing breaks because `merge_spec` writes the labels, but the confirmation is weaker than the classification it is supposed to confirm.

### F-6 (Medium) — the lab clock pin hides a live mixed-clock comparison rather than surfacing it

`spec/support/service_lab_context.rb:15-29` pins Ruby's clock with `travel_to(Time.current)` because `AcquireResourceLock` compares a lease written from `Time.current` against PostgreSQL `now()`. The builder's reasoning — that the harness holds one transaction open and production does not — is correct as far as it goes, and `AcquireResourceLock` is M01-15's and outside this boundary, so recording it as debt is the right call rather than fixing it here. What is a finding is the *effect*: with the clock pinned, no M01-18 example ever exercises lease expiry or re-acquisition with time moving, which is exactly the property AC7's fencing-token example (`service_restart_lab_spec.rb:41-48`) appears to cover and does not. The debt entry should name that, not only the arithmetic.

### F-7 (Low) — `nextCheckAt` exists only in the log line

The Story's Observability Requirement puts `nextCheckAt` on the `ReconciliationRun`; `service_reconciler.rb:478,483-487` emits it as a log field only, because no column exists. Recording that as a conflict rather than inventing a column is defensible — but the Story's own diff already adds a migration to `services`, so "undecidable here" is weaker than it reads; it was a choice not to widen the schema, and the report should say so in those words.

### F-8 (Low) — `env` remains in the create/update allowlist while the Story forbids env values

`swarm_executor.rb:39-42` keeps `env` in both service operations; `SpecTranslation.payload_for` never sets it and `service_workload_hardening_spec.rb:37-39` asserts the payload has no `:env`. Not a defect for M01-18 — the key is needed by M03 — but the only thing preventing a sensitive value reaching a container spec is the translator, not the boundary. Worth a line in the report so M03 inherits it consciously.
