### F-1 — closed, and it earned its keep

`e2e/panel.spec.ts` exists and runs the same analyzer on the delivered screens: `:184`
for projects and `:191` for clusters, audit and settings, plus sign-in and sign-up.
`AxeBuilder` with `wcag2a, wcag2aa, wcag21a, wcag21aa, wcag22aa` — the tag set
`smoke.spec.ts` already used.

**The two defects it found are the argument for the AC, and I confirmed both.**

- **The session cookie was `Secure` in an environment served over plain HTTP.**
  `app/controllers/concerns/authentication.rb:119` was `secure: !Rails.env.development?`.
  The E2E server runs `bin/rails server -e test` over `http://127.0.0.1:3999`
  (`playwright.config.ts:44-47`), so Chromium discarded every session cookie and every
  authenticated journey bounced back to `/sign_in` with no error at all. This is exactly
  the class of defect only a real browser finds: `https!` in a request spec sets the
  cookie, and jsdom has no cookie policy to enforce. Confirmed against my own round-1
  run, where all three authenticated journeys died at the same line.
- **Authentication landed on the M00 example page, not on the shell.**
  `authentication.rb:90-108` returned `root_path`; `registrations_controller.rb:34`
  redirected to `root_path`. AC1 says the authenticated user sees the app shell, and
  until this change signing in did not produce one. Confirmed by reading the diff and by
  `spec/requests/session_cookie_spec.rb:39`, whose expectation had to move from
  `root_path` to `teams_path`.

**Does `secure: request.ssl?` weaken anything? No — and I checked the way it could.**
The risk in keying the flag on the request rather than on the environment is a
TLS-terminating proxy: behind Traefik, Rails sees plaintext, `request.ssl?` is false and
the session cookie ships without `Secure`. That does not happen here, for two
independent reasons, both in `config/environments/production.rb`:

- `:25` — `config.assume_ssl = true`. Rack treats every request as SSL regardless of
  what the proxy forwards, so `request.ssl?` is true in production even with a
  terminating ingress.
- `:28` — `config.force_ssl = true`. A plaintext request is redirected before any action
  runs, so no cookie is ever set on one.

`spec/requests/session_cookie_spec.rb:34,55-56,84` still drives `https!` and asserts the
real `; secure` attribute, so the flag is proved rather than assumed. One residual,
recorded as L-3: the invariant moved from code into configuration, and nothing pins
those two settings.

### M-9 — the E2E teardown deletes rows that are not the journey's

- **Dimensão:** Dados / Operação
- **Severidade:** Medium
- **Evidência:** `e2e/support/global-teardown.ts:93-116`. The scoping is real for users
  (`email LIKE 'panel-%' OR 'diag-%'`) and teams (by owner, or `slug LIKE 'journey-%'`),
  and the delete order follows the `RESTRICT` foreign keys correctly. Three things are
  not scoped or not safe:
  1. **The final statement, `DELETE FROM authentication_attempts;` (`:115`), has no
     `WHERE` clause.** It empties the whole table, contradicting the function's own
     comment four lines above ("Scoped by the prefixes the journeys use, never a blanket
     wipe"). `authentication_attempts` is the lockout / rate-limit table from M01-01: a
     teardown that unconditionally clears it destroys whatever an integration spec or a
     developer had set up, and it is the wrong habit to write down in a file that runs
     `psql` against a database name taken from the environment.
  2. **A partial failure is silent.** The statements go to `psql -c` as one implicit
     transaction with `stdio: 'ignore'`, and the `catch` only warns. One foreign-key
     violation aborts the whole cleanup and the run still reports success — so the
     48-example contamination this function exists to prevent comes back invisibly.
     `team_members.invited_by` (`db/schema.rb:327`, `ON DELETE RESTRICT`) is not covered
     by the `DELETE FROM team_members` predicate, which is precisely such a violation
     waiting for the first journey that invites somebody.
  3. `diag-%` matches nothing in the repository — a prefix no test creates, deleting rows
     nobody writes.
- **Cenário de dano:** the second one is the expensive one: a future journey adds an
  invitation, the cleanup aborts on the FK, nothing says so, and the next `bin/test`
  fails 48 examples in files nobody touched. That is a day of somebody's week.
- **Ação:** open — scope `authentication_attempts` to the journey users, cover
  `invited_by`, and let the teardown report a failure instead of swallowing it.
- **Estado:** open

### M-10 — the panel screens waive all three baseline entries, and the waiver's own mitigation is now false

- **Dimensão:** Testes / Segurança (acessibilidade)
- **Severidade:** Medium
- **Evidência:** I was asked to contest this decision if I disagreed. **I agree with the
  decision and disagree with its implementation, on two specific points.**

  The decision itself — accepting `color-contrast` on the panel screens because the shell
  renders `shared/profile`, whose `AvatarFallback` measures 4.16:1 — is the right call.
  The alternatives really are worse (silence the check, drop the account menu, or patch a
  vendored component and create drift), the debt is owned and dated
  (`config/quality/waivers.yml:155-166`, expiring 2027-03-31), the expiry is still
  enforced by `e2e/gallery.spec.ts:62-77`, and it was declared in its own section rather
  than slipped in. Extending a *recorded* waiver to a new surface, in the open, is not the
  same act as weakening a gate.

  What is wrong:
  1. **`e2e/panel.spec.ts:65` waives every id in the baseline, not the one that was
     argued.** `Object.keys(baseline.violations)` is `color-contrast`,
     `aria-input-field-name` and `scrollable-region-focusable`. The last two are
     keyboard-reachability failures — a slider with no accessible name, a scroll region
     unreachable by keyboard — and nothing in the justification covers them. They are
     invisible today because the panel renders neither a `Slider` nor a `ScrollArea`; the
     day M01-07 puts a log pane in the panel, a keyboard-unreachable region passes AA on
     every panel screen and AC6 is quietly untrue. One line fixes it:
     `allowThemeDebt ? ['color-contrast'] : []`.
  2. **`config/quality/waivers.yml:163-164` now says something false.** The waiver's
     recorded mitigation is *"None of the three is used for essential text in Opanel's own
     pages"*. `muted-foreground` is now on the account menu of every authenticated page.
     The same is true of `e2e/accessibility-baseline.json`'s `$comment`, which still
     states *"Opanel's own pages carry no baseline"*. A waiver justified by a mitigation
     that has stopped being true is the smaller cousin of F-1: the reason of record
     outlives the Story, and the next reader believes it.
- **Ação:** open — narrow the waived set to `color-contrast`, and update the waiver's
  mitigation and the baseline comment to say what is now true.
- **Estado:** open
