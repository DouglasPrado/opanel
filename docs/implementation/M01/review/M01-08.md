## Findings

### F-1 — `SwarmBootstrap` inherits `DOCKER_HOST`/`DOCKER_CONTEXT` from the process environment, contradicting its own "the socket stays local" claim

- **Dimensão:** Arquitetura / Segurança
- **Severidade:** Critical
- **Evidência:** `app/executors/swarm_bootstrap.rb:162-173`, specifically line 167:
  ```ruby
  def capture(arguments, timeout)
    Timeout.timeout(timeout) do
      Open3.capture3("docker", *arguments)
    end
  ...
  ```
  with the comment immediately above it (`swarm_bootstrap.rb:164`) asserting *"No
  `DOCKER_HOST` is set and no `-H` is passed: the local socket is the only
  destination"* and the class comment at `swarm_bootstrap.rb:30-35` claiming this
  holds *"by construction rather than by configuration."* Neither is true:
  `Open3.capture3` inherits the calling process's environment unless told
  otherwise, and the `docker` CLI itself honours `DOCKER_HOST` (and, absent that,
  the current `docker context`) regardless of what `SwarmBootstrap` does or does
  not set.
- **Verificado, não apenas lido.** Reproduced directly against the real `docker`
  binary on this machine:
  ```
  $ DOCKER_HOST=tcp://192.0.2.1:2375 ruby -e 'Open3.capture3("docker","info",...)'
  status=pid ... exit 0
  err=Get "http://192.0.2.1:2375/v1.55/info": dial tcp 192.0.2.1:2375: i/o timeout
  ```
  The CLI attempted the remote endpoint, proving that any ambient `DOCKER_HOST`
  in the Rails process's environment — set by a deployment tool, an operator's
  shell profile inherited by a supervisor, a misconfigured secret, or an
  attacker who gains the ability to influence environment variables through any
  other channel — silently redirects every `SwarmBootstrap` operation
  (`info`, `init`, `label_node`) to a remote Engine. This is exactly the
  boundary this Story exists to protect: the Story's own Security Requirements
  say *"O navegador nunca fala com o Docker"* and doc 06 §4.2 requires the
  socket stay local to authorized components — but nothing here enforces that
  the *executor itself* only ever reaches the local socket, only that it does
  not *add* a remote destination on its own.
- **A prova de que o teste não pega isto.** `spec/security/docker_api_exposure_spec.rb:100-104`
  ("never sets `DOCKER_HOST` to a network address") only `grep`s the repository's
  own source for the literal string `DOCKER_HOST\s*=\s*["']?tcp:`. It cannot
  fail on the vulnerability demonstrated above, because the vulnerability is not
  a string in the repository — it is the absence of an explicit environment
  override at the one call site that shells out to `docker`. This is the same
  class of gap the task asked to attack specifically: a check that is worded as
  if it tests a runtime property but in fact tests only that nobody typed a
  particular string.
- **A ironia:** `lib/gates/swarm_lab.rb` (pre-existing tooling, not part of this
  Story's boundary) already implements exactly the right defence for the
  *disposable lab* — `resolved_endpoint`/`assert_claimable_endpoint!` explicitly
  resolve what `DOCKER_HOST`/`DOCKER_CONTEXT` would make the CLI talk to, and
  refuse to mutate anything that is not a claimed, loopback-resolving,
  allowlisted endpoint. The production executor added by this Story, which is
  the one that will run against a real Engine in a real installation, has no
  equivalent guard at all.
- **Cenário de falha concreto:** an installation's Control Plane process
  inherits `DOCKER_HOST=tcp://10.x.x.x:2375` from its environment (e.g. a
  container orchestration layer that sets it for an unrelated purpose, or a
  supervisor process that exports it). An `INSTANCE_ADMIN` clicks "Initialize
  cluster." `BootstrapCluster` runs the full preflight against *this* host,
  passes it, and then `SwarmBootstrap.init` silently runs `docker swarm init`
  against the remote host named by `DOCKER_HOST` instead — turning an unrelated
  or attacker-controlled machine into the manager of record for this
  installation's Swarm, with the Control Plane none the wiser and the UI
  reporting success.
- **Ação:** open — the executor's `capture`/`run!` boundary needs to pin the
  destination explicitly (e.g. pass `env: { "DOCKER_HOST" => nil, "DOCKER_CONTEXT" => nil }`
  to `Open3.capture3`, or resolve and assert a local unix socket the way
  `swarm_lab.rb` already does for the lab), and the security spec needs a
  behavioural assertion — not a source grep — that proves it.
- **Estado:** closed — re-verified against the real fix in Round 2 below.

### F-2 — AC1's real `swarm init` path cannot run even under the documented opt-in, on any machine

- **Dimensão:** Testes / Correção
- **Severidade:** Critical
- **Evidência:** `spec/integration/swarm_bootstrap_lab_spec.rb:154-229` ("initialising
  an empty daemon (AC1)"), gated by `OPANEL_SWARM_DESTRUCTIVE=1`. Per the task's
  explicit instruction, I ran it with the flag set, against the lab confirmed
  `up` beforehand (`bin/swarm-lab status` → `swarm active, 1 node(s)`):
  ```
  $ OPANEL_SWARM_DESTRUCTIVE=1 bundle exec rspec spec/integration/swarm_bootstrap_lab_spec.rb
  12 examples, 0 failures, 2 pending
  Pending:
    1) ... initialising an empty daemon (AC1) turns an inactive daemon into a Swarm ...
       # this Docker daemon is not the Opanel lab — run `bin/swarm-lab up`.
    2) ... initialising an empty daemon (AC1) leaks no join token from a real initialisation
       # this Docker daemon is not the Opanel lab — run `bin/swarm-lab up`.
  ```
  Both examples the report claims are "proven on demand" are **still skipped**,
  and skipped for a *different* reason than the documented opt-in message
  (`"initialising a Swarm needs a daemon that is not in one..."`, defined at
  `swarm_bootstrap_lab_spec.rb:168-172`). The message actually shown —
  `"this Docker daemon is not the Opanel lab"` — comes from the **global**
  `:swarm` guard at `spec/support/swarm_lab.rb:143-145`, which is pre-existing
  test infrastructure outside this Story's boundary.
- **Causa raiz, verificada.** The example's own `around` block
  (`swarm_bootstrap_lab_spec.rb:175-188`) runs `Opanel::Gates::SwarmLab.docker!("swarm", "leave", "--force")`
  *before* `example.run`. `example.run` is what triggers RSpec's `before(:each, :swarm)`
  hooks, including the global one that calls `lab_daemon?` — but the node has
  just left the Swarm, so `docker node inspect self` (what `lab_daemon?` shells
  out to) fails: there is no "self" node to inspect outside a Swarm. `lab_daemon?`
  therefore returns `false`, and the **global** guard hook `skip`s the example
  before its own local `before` block (which checks `OPANEL_SWARM_DESTRUCTIVE`)
  or its body ever runs. I confirmed this is exactly what happened by checking
  the lab's own restoration afterwards: `bin/swarm-lab status` still reported
  `up`, which only the `around` block's `ensure` (re-init + re-label) can
  produce — proving the body between "leave" and the assertions never executed,
  the `ensure` did, and the skip fired mid-flight rather than never reaching the
  `around` block at all.
- **Isto não é o padrão honesto de diferimento da `M01-07` AC5.** `M01-07`'s AC5
  was named as unmet because the dependency (`Environment`) genuinely does not
  exist yet, and the report said so plainly. Here the report presents the same
  shape — *"os dois exemplos ... ficam atrás de `OPANEL_SWARM_DESTRUCTIVE=1` e
  são skipped com a razão declarada, nunca reportados como passando"* — but the
  claim that setting the flag *proves the path* is false: the flag changes
  nothing about whether the example runs, because a different, pre-existing
  guard intercepts it first for an unrelated reason. `grep -rln "SwarmBootstrap.init"`
  across `spec/` finds exactly one file (`docker_api_exposure_spec.rb`), where
  it is stubbed, not real. **`docker swarm init` is never actually invoked by
  any test in this repository, on this machine or (structurally) on any
  machine**, which directly contradicts the Definition of Done's *"Os 11
  Acceptance Criteria satisfeitos contra Swarm real"* for AC1's central claim
  ("uma instalação vazia inicializa um Swarm"), and contradicts the Story's own
  Required Tests ("Docker/Swarm: init e leitura de `swarmId`").
- **Cenário de falha concreto:** a regression in `SwarmBootstrap.init` — say, a
  future edit that passes the wrong flag to `swarm init`, or breaks the
  read-back of `swarm_id` — ships green, because the one test positioned to
  catch it against a real daemon is permanently, silently skipped by a hook
  ordering bug, not by the documented and reviewable opt-in gate.
- **Ação:** open — fix the `around` hook so it re-applies the lab label (or
  otherwise satisfies `lab_daemon?`) before `example.run` reaches the global
  guard, or restructure the guard check to run once at the `describe` level
  rather than per-example; then re-run with `OPANEL_SWARM_DESTRUCTIVE=1` and
  confirm the two examples actually execute (not merely "0 failures, N
  pending"). This is a defect in test infrastructure spanning a file inside
  this Story's boundary (`swarm_bootstrap_lab_spec.rb`) and one outside it
  (`spec/support/swarm_lab.rb`); either can carry the fix, but the Story cannot
  claim AC1 proven against a real Engine until one of them does.
- **Estado:** closed — re-verified against the real fix in Round 2 below.

### F-3 — an explicit advertise address with unreadable interfaces raises `NoMethodError` instead of a typed refusal

- **Dimensão:** Correção / Testes
- **Severidade:** Medium
- **Evidência:** `app/commands/bootstrap_cluster.rb:186-193`:
  ```ruby
  def chosen_advertise_address(report)
    if advertise_address
      known = report.interfaces.map(&:address)
      ...
  ```
  `report.interfaces` is `nil` whenever `SystemProbe#interfaces` cannot enumerate
  the machine's addresses (`app/clusters/system_probe.rb:105-107`, rescuing
  `SystemCallError`) — a case the codebase treats as a first-class, distinct
  outcome everywhere else (`interfaces_known?`, `advertise_candidates` defaulting
  to `[]`). Reproduced directly:
  ```
  result.interfaces = nil
  result.interfaces.map(&:address)
  # NoMethodError: undefined method 'map' for nil
  ```
  When `interfaces` is `nil` and the operator supplies an explicit
  `advertiseAddress` (a normal UI action, not a misuse), this line raises
  unhandled inside `BootstrapCluster#call`, which has no `rescue` for
  `NoMethodError` — surfacing as an unhandled 500 rather than the
  `VALIDATION_ERROR("ADVERTISE_UNKNOWN")` every other malformed-address path
  produces. No test in `spec/integration/cluster_bootstrap_spec.rb` exercises
  `interfaces: nil` together with an explicit address (confirmed by grep: the
  only `interfaces:` fixtures used are concrete arrays).
- **Cenário de falha concreto:** on a host where interface enumeration fails
  transiently (a container without `NET_ADMIN`, a sandboxed CI runner, a rare
  `Socket.getifaddrs` failure), an operator who already knows the address they
  want to advertise on submits it anyway and gets an unhandled exception page
  instead of a diagnosable refusal.
- **Ação:** open — guard `chosen_advertise_address` for `report.interfaces_known?`
  before mapping, returning `ADVERTISE_UNKNOWN` (or a new, honestly-named
  failure) when interfaces could not be enumerated at all; add the missing test.
- **Estado:** closed — re-verified against the real fix in Round 2 below.

### F-4 — `cluster_bootstrap_failed` is declared as an audit action and never emitted; failed bootstrap attempts past authorization are not audited

- **Dimensão:** Observabilidade
- **Severidade:** Medium
- **Evidência:** `app/models/audit_log.rb:33-35` and `spec/unit/audit_actions_spec.rb:32`
  both declare `cluster_bootstrap_failed: "cluster.bootstrap_failed"`.
  `grep -rn "AuditTrail.record"` across `app/` shows only two call sites in
  `BootstrapCluster` — both on the *success* paths (`persist`, for
  `:cluster_bootstrapped`/`:cluster_adopted`). The failure paths
  (`blocked`, `unreachable`, `failure`, `app/commands/bootstrap_cluster.rb:259-283`)
  write only to `Rails.logger`, never to `AuditLog`. A denied *authorization*
  attempt is still audited (via `Opanel::Authorization.record`), but a
  *preflight-blocked* or *engine-unreachable* bootstrap attempt by a correctly
  authorized `INSTANCE_ADMIN` — i.e. a real, privileged action that was
  attempted and failed — leaves no audit trail at all, only an application log
  line that an operator investigating after the fact may not have retained.
- **Por que importa aqui.** The Story's own Security Requirements state
  *"Bootstrap exige `INSTANCE_ADMIN` e é auditado"*, and `AGENT_RULES`'s Audit
  section asks that a privileged action's audit record include the `result`,
  not only its success. Declaring the vocabulary entry and then never using it
  reads as an intended behaviour that was not finished, not a deliberate
  scope decision recorded anywhere in the report's "Pendências" section.
- **Cenário de falha concreto:** three consecutive engine-unreachable bootstrap
  attempts by an `INSTANCE_ADMIN` (e.g. someone probing whether the daemon is
  up) produce zero `AuditLog` rows; reconstructing "who tried to bootstrap this
  installation, and how many times, before it finally worked" after the fact
  depends entirely on whichever application log retention policy happens to be
  in place, which the audit trail exists specifically not to depend on.
- **Ação:** open — either call `AuditTrail.record(action: :cluster_bootstrap_failed, ...)`
  from the failure paths, or remove the unused vocabulary entry and record in
  the report why failed attempts are logged-only.
- **Estado:** closed — re-verified against the real fix in Round 2 below.

## F-1 — closed, verified live against the real fix

`SwarmBootstrap.endpoint` resolves `DOCKER_HOST`, then `docker context inspect`,
and `assert_local_endpoint!` refuses anything whose scheme is not `unix`/`npipe`
**before** `run!` calls `capture`. Re-ran the coordinator's exact attack against
the real code, not the spec:

```
DOCKER_HOST=tcp://192.0.2.1:2376 bundle exec rails runner '...SwarmBootstrap.info...SwarmBootstrap.init(...)...'
refused: DAEMON_NOT_LOCAL
init refused: DAEMON_NOT_LOCAL
```

Both calls refused instantly (no 20s network timeout), proving the check runs
before any subprocess touches the network. Also tried a schemeless value
(`DOCKER_HOST=192.0.2.1:2376`) → `DAEMON_ENDPOINT_UNKNOWN`, correctly refused
rather than guessed. Then mutated `assert_local_endpoint!` to `true` (a no-op)
and reran the new spec section: 4 of 5 new examples failed correctly, including
one that took the full real-network timeout path (`refuses an SSH endpoint too`,
`refuses a TCP endpoint before running anything`) because the guard was gone and
a real `Open3.capture3` call was attempted against `192.0.2.1` — the mutation
was genuinely exercised, not short-circuited by a mock. Restored and diffed
identical to backup. **Estado: closed.**

## F-2 — closed, with first-hand evidence stronger than what the report captured

The AC1 example carries no `PENDING` annotation and is absent from the failures

full file afterwards (`11 examples, 0 failures, 1 pending`, the pending one
correctly reporting "already in a Swarm" — the honest, on-topic skip reason,
