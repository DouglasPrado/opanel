## Architecture Invariants

**Critical Issue — High Severity:**

`PublishPendingOutboxEvents` creates a `SolidQueue::Job` and marks the `OutboxEvent` as published without transactional atomicity, violating the invariant "Desired State + Operation + Outbox event commit in one transaction" (AGENT_RULES §"Async Operations").

**Location:** `/Users/douglasprado/www/opanel/app/commands/publish_pending_outbox_events.rb` lines 39–67. Specifically:
- Line 44: `publish_to_queue(queue, event)` creates `SolidQueue::Job.create!`
- Line 48: `event.mark_published!` updates the OutboxEvent

These are not wrapped in a single `ActiveRecord::Base.transaction` block. The code comment at lines 46–47 states "Mark event as published in the same transaction that published it," but the implementation does not guarantee this. If line 44 succeeds and line 48 fails, the job is created but the event remains unpublished, violating one-transaction semantics.

**Impact:** While the system remains eventually consistent due to the periodic sweep and inbox dedup, the architectural rule explicitly forbids this race condition. A proper fix would wrap both operations:
```ruby
ActiveRecord::Base.transaction do
  SolidQueue::Job.create!(...)
  event.mark_published!
end
```

**Network calls in transactions:** No violations found. The `QueueBackpressure.active?` check at line 236 of `update_service_desired_state.rb` performs only a database count; no network calls inside the transaction.

## Item 2: Test Assertion — NOT FIXED / HIGH FINDING

**Claim:** The new example should assert both that the event stays unpublished AND that no Job row survives.

**Arbiter's directive:** Gain the example where `mark_published!` raises and assert both conditions.

**Implementation:** Lines 74–93 of `spec/integration/outbox_dispatcher_spec.rb` has the example with both assertions:
- Line 88: `expect(event.reload.published_at).to be_nil`
- Line 92: `expect(SolidQueue::Job.count).to eq(0)`

**Critical Issue:** The test is a weakened test that claims to prove something it does not prove.

The example runs **inside RSpec's transactional fixture** (`spec/rails_helper.rb:25` sets `config.use_transactional_fixtures = true`, and the example has no `:concurrent` tag). When mark_published! raises:

1. The command's `ActiveRecord::Base.transaction do` creates a savepoint
2. The Job is inserted into the savepoint
3. mark_published! raises
4. The savepoint rolls back
5. **But the entire example is also in RSpec's outer transaction**
6. When the example ends, RSpec rolls back its outer transaction, wiping all traces

The test **cannot distinguish** whether it passed because:
- The command's transaction correctly rolled back the Job, OR
- RSpec's fixture transaction rolled back everything

To actually prove transactional behavior, the example would need either the `:concurrent` tag (to disable transactional fixtures) or be structured to verify the rollback from outside the transaction.

The comment at line 79 states "This proves the transaction: if mark_published! fails, the job row does not survive." But the test passes for the wrong reason — RSpec's fixture, not the command's transaction. A maintainer reading this comment would think the transaction is tested, when it is not.

**Severity:** HIGH — This is a weakened test. It claims to test transactional safety but passes for reasons that have nothing to do with the transaction.
