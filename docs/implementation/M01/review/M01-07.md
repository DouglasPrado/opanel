## Findings

### F-1 — AC5 is not met, and no test can prove it

- **Dimensão:** Correção / Testes
- **Severidade:** Critical
- **Evidência:** `docs/implementation/M01/stories/M01-07-project-entity.md:69` (AC5 —
  "Arquivar um Project com Environments ativos é bloqueado com erro explicativo").
  `app/commands/archive_project.rb:46` carries a `TODO(M01-11)` in place of the guard.
  `spec/unit/project_lifecycle_spec.rb:95-101` asserts the table `environments` does
  not exist and that archiving *succeeds* — the inverse of what AC5 asks for. Confirmed
  independently: `git grep -l "class Environment\|create_table :environments" -- app lib db`
  returns nothing, and `docs/implementation/M01/stories/M01-11-environment-entity.md:15`
  does list `M01-07` as one of its own preconditions — the circular dependency the report
  and `docs/implementation/SPEC_CONFLICTS.md` (`SC-18`) describe is real, not invented
  after the fact.
- **Por que ainda bloqueia, apesar de bem tratado.** The way this was handled is the
  correct procedure under `AGENT_RULES`'s "Specification Conflicts": the conflict is
  named, the affected part alone is stopped, the rest of the Story proceeds, and the
  report does not claim coverage it does not have — which is the opposite of the
  `M01-06` failure this Story explicitly set out not to repeat. None of that changes
  what the Definition of Done requires: *"Os 9 Acceptance Criteria satisfeitos"*. Eight
  are. A criterion nobody can currently write a test for is not a satisfied criterion,
  and the severity table is explicit that an unmet acceptance criterion is Critical
  regardless of how honestly the gap is disclosed. This is a defect in the Milestone's
  own dependency plan (the two Stories precondition each other), not a defect the
  implementer introduced or could have closed without doing `M01-11`'s job inside this
  Story's boundary — the report is right that creating `environments` here would be
  scope creep in the other direction. The right resolution is a human/orchestrator
  decision on the plan (reorder the two Stories, or accept AC5 as formally owed to
  `M01-11` before either is marked `done`), not a silent pass of this Story to DONE.
- **Cenário de falha concreto:** ship this Story as `done` today, and archiving a
  Project with an active Environment is unenforced in production for as long as
  `M01-11` is not merged and its own AC5 obligation (named in `SPEC_CONFLICTS.md`) is
  not fulfilled — nothing here currently makes that consequence visible outside this
  review and the SC-18 entry.
- **Ação:** open — track as the named obligation on `M01-11` (already recorded in
  `SC-18`); do not mark `M01-07` `done` while this AC remains unverifiable, or obtain
  an explicit human decision that accepts the deferral against the Definition of Done.
- **Estado:** open

## Answering the coordinator's specific questions

- **O spec do `ProjectOverview` discrimina?** Yes, on all three attempts —
  `raise`, `policy.archive? → true`, and `project.external_id → project.id` —
  each caught by a distinct, correctly-worded failure. See F-2 above.
- **A tela nova — o botão de arquivar testado nos dois sentidos?** Yes.
  `spec/frontend/project-page.test.tsx:115-136` covers presence (`permissions.archive:
  true`, `status: 'ACTIVE'` — the default), absence by permission (`permissions:
  { archive: false }`, a DEVELOPER) and absence by state (`status: 'ARCHIVED'`
  with `permissions.archive` still `true`). I mutated the component to drop the
  `project.status === 'ACTIVE'` half of the guard and the third case caught it
  immediately (`does not offer to archive a project that already is` failed,
  showing the button rendered when it should not have). Restored and diffed
  clean.
- **A ausência de diálogo de confirmação — doc 10 §26 ou finding?** Justified.
  `docs/architecture/10-ui-use-cases.md:806-818` (§26) lists exactly eight
  actions requiring confirmation — Delete Service, Delete Environment, Remove
  Node, Demote Manager, Delete Secret, Rotate Recovery Key, Transfer Owner,
  Restore — and Archive Project is not one of them, consistently with the
  table's own logic: every listed action either destroys data, changes quorum,
  or moves ownership, and archiving a Project does none of that in this
  Milestone (the row stays, `M02-09` is what tombstones it). The card's own copy
  states the consequence before the click (*"stops appearing in the list. It
  cannot be edited afterwards."*), which is the doc's own alternative to a modal
  for a low-risk action. No finding.
- **A rota `GET` nova entrou no harness cross-team?** No — by the harness's own
  design, `AuthorizationHarness.mutating_routes` excludes every `GET`
  (`spec/support/authorization.rb:76-88`), with a comment naming
  `spec/security/authorization_disclosure_spec.rb` as where GET disclosure is
  supposed to live. That file was not touched this round and still only covers
  `GET /teams/:id`. **This does not open a real hole**: `show`, `update` and
  `archive` all resolve the Project through the same private `scoped_project`
  (`app/controllers/projects_controller.rb:91-99`), so a cross-team `GET` and a
  cross-team `PATCH` fail identically by construction, not by parallel
  maintenance of two checks — and I proved the `GET` case specifically fails
  correctly by the same tenant-scope-removal mutation used for F-2 above.
  `spec/requests/projects_spec.rb:208-216` ("reading one … answers a Project of
  another Team as absent") exercises exactly this, just not via the
  byte-for-byte `normalize`-and-compare technique `authorization_disclosure_spec.rb`
  uses for other resources. I record the inconsistency as M-1's sibling in spirit
  but do not file a separate entry for it: the comment's promise is stale and the
  stronger structural guarantee (one shared private method, not two independent
  code paths) is what actually holds here, which is a better proof than a second
  parallel spec file would add. If the maintainers want the same technique
  applied uniformly, that is a Low follow-up, not a gap in coverage.
- **Escopo — a tela é da `M01-22`?** No, and the distinction holds up under
  scrutiny. `M01-22`'s doc 10 §7.1/§7.3 content — production status, environment
  counts, last deploy, attention, "Recent releases", "Incidents", "Environment
  comparison", "[Create Environment]" — is entirely absent from `Project.tsx`,
  and the file's own comment names each of those as needing `M01-11`, `M01-12`
  through `M01-18`, and `M01-19` first. What shipped is exactly what this
  Story's own `Application Layer` section already named as required
  (`ProjectOverview` — *"versão mínima do doc 09 §23"*) plus the one caller
  UC-009 requires for it. Building the minimal version now, rather than leaving
  the Query with no caller until `M01-22`, is closing this Story's own scope, not
  borrowing the next one's.
