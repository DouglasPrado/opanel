## 3. Architecture invariants

**Finding C-1 (Critical) — the executor is not isolated from the public
Control Plane process it is supposed to be isolated from.**

Doc 07 §2.2 is explicit and gives a diagram: `API / Workers --[internal
authenticated RPC]--> Swarm Executor --[/var/run/docker.sock]--> Docker
Engine`, and lists as **not allowed**: `Public API -----X--------> docker.sock`.
It also says replicas of the Executor exist "para disponibilidade" — a
separately scaled unit. `AGENT_RULES.md` restates the same invariant: "The
Docker socket is isolated. The public API, the web UI, ordinary workers and
builders never touch `/var/run/docker.sock`." Annex C rates the Executor
Tier-0/T01, CRITICAL, precisely because socket access is root-equivalent.

What is built is `app/executors/*.rb`, plain Ruby classes under Zeitwerk
autoload in the single `Opanel::Application` (`config/application.rb`) — the
same monolithic Rails process that boots `app/controllers/**`. There is no
Procfile, no separate service, no RPC boundary; I confirmed this by reading
`config/application.rb` (`Bundler.require` / `Rails::Application` singular
config, no split web/executor boot path) and by the fact `bin/swarm-lab`,
routes and stack files show one process. This means the process that serves
public HTTP requests **does** hold the Docker socket privilege in-memory —
exactly the arrangement doc 07 §2.2 draws an "X" through. "No public route
reaches it" (AC1/AC10, both proved and both real) narrows the *routing*
surface but does not restore the *process* boundary: an RCE, insecure
deserialization or any other memory-corruption/code-injection bug anywhere
else in that same Rails process reaches `SwarmExecutor`/`EngineClient`
directly, no RPC hop to defeat.

The report registers this as a known divergence ("Divergência de forma, não de
invariante; registrada... a Story já escolhe"), and the Story's own Scope
section does say "Módulo `app/executors/`". But `AGENT_RULES.md`'s precedence
is explicit: approved architecture outranks the current Story, and "a lower
level may never contradict [a higher one]." A Story clause that contradicts an
explicit, security-critical architecture diagram is exactly the case
"Specification Conflicts" is written for: record it, explain the impact, and
stop the affected part — pending an ADR or a human/product decision — not
implement it and note the gap in the report. No ADR exists for this
divergence. This blocks DONE: it is a broken architecture invariant (socket
isolation) on a Tier-0 component, not a Medium documentation debt.

Everything else in this section — Desired/Actual separation (none touched;
correctly out of scope), MCP path (untouched), one-transaction writes (the
executor makes no DB writes and no writes inside a transaction; correct, it
persists nothing) — no further finding.

## 4. Security

**Finding H-1 (High) — `update_service_spec`'s CAS is optional, and omitting
it reproduces the exact CLI hazard the transport choice was meant to avoid.**

`app/executors/swarm_executor.rb:136`:
```ruby
version = command.payload.fetch("version", version_of(current.body))
```
When the caller supplies `payload["version"]` (the value it observed when it
computed its diff), this is real CAS: the Engine will reject a version that
moved underneath it, which the lab spec proves (`swarm_executor_lab_spec.rb`
"refuses a stale version"). But when the caller omits it, the executor
substitutes the version it *just read in the same call* — i.e. it performs
exactly the read-then-write-blind sequence the plan explicitly rejected the
CLI for ("a CLI... lê a versão sozinha e faz read-modify-write cego"). A
reconciler that diffs against an older observed revision and then calls
`update_service_spec` without threading its own observed `version` through
gets no conflict signal at all, silently overwriting whatever changed the
Service between the reconciler's diff and this call — the precise race doc 07
§5.3's "Conflito de versão" row exists to catch. `ExecutorCommand#desired_revision`
(the doc 07 §20.1 field, confirmed present and confirmed unused anywhere in
`swarm_executor.rb` by `grep`) is not consulted either, so there is no
contract-level requirement that a caller supply an expected baseline at all.
This is not hypothetical: `spec/unit/swarm_executor_spec.rb:316` ("sends the
version it observed when the command carries none") encodes the omission path
as intended, expected, passing behavior rather than as a forbidden one — there
is no negative test proving that a caller who omits `version` gets a rejected
write when the Service changed in between. Fix: require `version` for
`update_service_spec` (raise in `validate!`/`guarded` when absent) rather than
silently defaulting to a fresh read.

**Finding M-1 (Medium) — the connect-timeout/transfer-timeout curl heuristic
is validated only against a fabricated stderr string, and real `curl` on this
machine does not produce that string.**

`app/executors/engine_client.rb:150` distinguishes "connect timed out"
(transient) from "transfer timed out after connecting" (unknown outcome) by
matching `stderr` against `/connection timed out|failed to connect/i`. I
reproduced both a stalled-connect (full accept backlog) and a stalled-transfer
unix-socket scenario with real `curl` and in both cases the message was
identical: `curl: (28) Operation timed out after Nms with 0 bytes received` —
never "Connection timed out" or "Failed to connect". `spec/unit/engine_client_spec.rb:118`
("classifies a connect timeout on a mutation as transient") passes only
because it stubs `Open3.capture3` with a synthetic stderr string
(`"curl: (28) Connection timed out after 5000 milliseconds"`) that this curl
version never emits for a unix socket. The safe side of this (misclassifying
a should-be-transient failure as `unknown` → `observe_before_retry`) is not
dangerous, but the code's own documented rationale for the distinction is
unverified against the transport it actually shells out to, and the
Docker/Swarm integration suite exercises no transport-failure path at all
(only unit-level stubs). Worth a lab-backed regression before this
distinction is relied on for anything less conservative than "always observe
before retry."

Other security items: SSRF — no URL-fetching feature added (out of scope,
correctly). Authorization — the executor correctly does not decide product
authorization (Annex I §4.1) and the Story is right that this isn't its job;
no finding. Secrets in payload — `ExecutorCommand#validate!` walks the payload
recursively against `Opanel::Redaction.sensitive_key?`, proved with a nested
key. No finding. Untrusted input at the allowlist boundary — `identifier()`
enforces `RUNTIME_IDENTIFIER` on every id interpolated into a URL path;
`find_by_label`'s filter uses the raw `resource_id` but only inside
`JSON.generate` then `CGI.escape`, so it cannot escape the query string even
though it skips `identifier()` — safe by construction, but inconsistent
(Low, §7 below).

disabled, or given an assertion that cannot fail; all six mutation attempts in

## 6. Observability

Every call logs `event`, `command_id`, `correlation_id`, `request_id`,
`resource_type/id`, `cluster_id`, `duration_ms`, `outcome`, `error_code`,
`observed_runtime_version`, `runtime_resource_ids`, and a redacted `transport`
message — never a body (proved by "never logs a response body"). A degraded
Engine is surfaced as `RETRYABLE`/`ENGINE_UNAVAILABLE`, never silently as
healthy. No finding.

## 7. Dependencies

No gem added. `curl` is a system binary already relied on for `docker`
(M01-08); the report documents evaluating and rejecting a Docker client gem.
Acceptable per "Does the approved stack already solve this? Is it
proportional?" — `Net::HTTP` cannot dial a unix socket and a dependency for
one transport was judged disproportionate. No finding on this axis, though
see M-1 above on unverified assumptions about `curl`'s own behavior.

**Finding L-1 (Low) — `find_by_label` does not run the caller-supplied
`resource_id` through `identifier()` before embedding it in a filter, unlike
every other operation.** It is safe today only because `JSON.generate` +
`CGI.escape` fully encode it before it reaches the URL; a future edit that
builds any path from `resource_id` without going through the same
serialize-then-escape discipline would not have the `identifier()` net that
protects every other operation. Add the `identifier()` check for consistency
even though no exploitable path exists today.

## 8. Report accuracy

I could not find a report claim contradicted by the repository, other than
the C-1 point above where the report's own framing ("Divergência de forma, não
de invariante") is the disputed claim itself — the repository's diagram in
doc 07 §2.2 disagrees with "not an invariant." Everything else checked
(command/exit-code counts, gitleaks residue fix, the four "mutations seen
fail" claims, the lab being left clean) reproduced as described.

## Findings summary

- **C-1 (Critical)** — Executor runs as an in-process module inside the same
  Rails application that serves the public Control Plane, not behind the
  internal authenticated RPC boundary doc 07 §2.2 requires; the public
  process holds Docker-socket-capable code in-memory, which the architecture
  explicitly forbids. No ADR resolves the divergence. `app/executors/*.rb`,
  `config/application.rb`.
- **H-1 (High)** — `do_update_service_spec` (`app/executors/swarm_executor.rb:136`)
  performs an unguarded read-modify-write, identical in effect to the CLI
  hazard the Story rejected, whenever the caller omits `payload["version"]`;
  no field is required, `desired_revision` is unused, and the omission path is
  encoded as expected behavior in `spec/unit/swarm_executor_spec.rb:316`
  rather than forbidden.
- **M-1 (Medium)** — `EngineClient#classify_transport_failure`'s
  connect-vs-transfer-timeout distinction (`app/executors/engine_client.rb:150`)
  is proved only against a stderr string real `curl` does not produce on this
  host for a unix socket (verified experimentally); safe-side misclassification
  only, but the documented rationale is unverified against the real transport.
- **L-1 (Low)** — `find_by_label` (`app/executors/swarm_executor.rb:276`)
  skips the `identifier()` check applied everywhere else; safe today only by
  virtue of JSON+CGI encoding, not by the same explicit guard.

## C-1 (Critical) — treatment reviewed, correctly left open

`SC-19` in `docs/implementation/SPEC_CONFLICTS.md` names the exact conflict
(doc 07 §2.2's RPC diagram vs. the in-process module), states the impact
(Tier-0/T01, no ADR, Story cannot outrank architecture), and offers the two
legitimate resolutions (ADR accepting the module for M01 with a named exit, or
an ADR demanding the separate service now) without inventing a third pattern
in between — which is the correct response to a security-architecture
conflict per `AGENT_RULES.md`. `BLOCKERS.md` records `BLOCKED_FOR_PRODUCT_DECISION`
and is explicit that `M01-17`/`M01-18` may still consume the module while the
Story itself does not close. `boundaries.yml` declares the new
`SPEC_CONFLICTS.md` touch. This is the right procedural move, and I did not
find a claim in it the repository disagrees with. **C-1 stays open** — a
recorded conflict is not a fix, and none was claimed to be one. Counted as
Critical.

## H-1 (High) — closed, confirmed by mutation

`app/executors/swarm_executor.rb:140-145` now raises `ExecutorCommand::Invalid`
before any Engine call when `payload["version"]` is absent; the fallback to a
freshly-read version is gone. I reverted the guard to the old
`command.payload.fetch("version", version_of(current.body))` fallback and
re-ran `spec/unit/swarm_executor_spec.rb:323` ("refuses an update that carries
no observed version, and sends nothing") — it failed as expected ("nothing was
raised"), then passed again once the guard was restored. The lab spec already
threaded `version:` through both updates, so the real-Engine path is
unaffected (7/0, reconfirmed). **Closed.**

## M-1 (Medium) — closed, confirmed by mutation

`app/executors/engine_client.rb:140-163` dropped the stderr-string heuristic;
every timeout (`exit 28`) on a mutating verb is now unconditionally `:unknown`,
and every timeout on a read is `:transient` — no attempt to distinguish
connect-phase from transfer-phase by message text, which is the right call
given curl reports the identical string for both on a unix socket, as this
review reproduced in Round 1. I reintroduced the old
`&& !detail.match?(/connection timed out|failed to connect/i)` condition and
re-ran `spec/unit/engine_client_spec.rb:123` ("classifies every timeout on a
mutation as unknown, whatever curl says") — it failed as expected (got
`transient` instead of `unknown`), then passed again once reverted. **Closed.**

## L-1 (Low) — code fixed, but the fix itself is unverified by any test

`app/executors/swarm_executor.rb:290-291` now reads
`identifier(resource_id)` inside `find_by_label`, so a malicious id reaching
`create_service`/`create_network` is rejected the same way it already was for
`inspect_service`/`remove_service`/etc. Confirmed present in the diff. But
unlike H-1 and M-1, **this one does not close by mutation**: I reverted
`find_by_label` to the un-guarded `"#{RESOURCE_LABEL}=#{resource_id}"` form and
ran the full unit/contract/security suite (53 examples) — nothing failed.
There is still no test that drives `create_service` or `create_network` with a
`resource_id` shaped like `s1/../../networks?x=1` (the exact fixture the
existing `inspect_service` test at `spec/unit/swarm_executor_spec.rb:99` uses
for the other operations). The guard is real and correctly placed, but a
future edit could remove it again with nothing to catch the regression. Given
the underlying string was already inert (`JSON.generate` + `CGI.escape` fully
encode it before it reaches a URL, as found in Round 1), this remains a Low
finding, now downgraded from "missing guard" to "guard present, untested" —
still worth one more example before it counts as proven rather than believed.
