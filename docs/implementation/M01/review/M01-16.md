### Finding 1: Test Cleanup Defect — Orphaned Swarm Resources

**Severity: Medium**

**Location:** Test cleanup code in `spec/integration/swarm_ownership_*.rb` (lines ~40–52 in swarm_ownership_labels_spec.rb, similar in other integration tests).

**Description:** The report states "Swarm lab cleanup verified green (`docker service ls` empty)" at line 86 of `docs/implementation/M01/reports/M01-16.md`. However, after the final test run, seven services remain on the lab daemon with complete `com.opanel.*` label sets, identifiable as created by this Story's tests. Test cleanup code attempts removal (via executor.execute with remove_service/remove_network commands), but cleanup is not reliable. These services carry ownership labels but lack the harness marker labels (`opanel.lab=true` and `opanel-lab` prefix) required by `config/architecture/docker-lab.yml:25,29`, preventing automatic reclamation.

**Evidence:**
- Report claims cleanup verified but orphaned services remain in daemon.
- Cleanup code at lines 40–52, 77–88, 130–140, 177–188 uses begin/rescue/raise pattern that re-throws exceptions if cleanup fails, which would cause test failure; yet tests report passing.
- Seven named services in daemon: `reidentify-service`, `service-1-reidentify`, `service-2-reidentify`, `svc-0-80347-1`, `svc-0-90482-1`, `svc-reident-0-80347-1`, `svc-reident-0-90482-1` — all carry `com.opanel.*` labels but not harness labels.

**Impact:** Test infrastructure brittleness. While the ownership labeling logic itself is correct, the test cleanup does not reliably return the Swarm to its initial state. This indicates either network isolation issues between test executor and daemon, race conditions in resource deletion, or a gap in teardown coverage. Does not affect production code or the correctness of the ownership predicate.

**Responsibility:** `spec/integration/swarm_ownership_labels_spec.rb`, `spec/integration/swarm_ownership_foreign_resource_spec.rb`, `spec/integration/swarm_executor_lab_spec.rb`.
